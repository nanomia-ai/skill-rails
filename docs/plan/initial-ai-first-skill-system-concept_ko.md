# 스킬을 만드는 스킬 — 범용 AI 스킬 시스템 최초 원점 기획

문서 정체성: 최초 방향성 기획

현재 상태: **동결됨 — 수정 금지**

결정 소유자: **사용자·프로젝트 소유자**

현재 결정: 기존 Skill Rails와 Devflow의 계획·구현을 기준선으로 고치지 않고, 과거 자료는 격리된 증거로 보존한 채 스킬을 만드는 스킬을 greenfield로 다시 설계한다.

동결 시점: **2026-09-13 KST — 사용자가 최초 기획의 완료와 동결을 확인함**

동결 후 정책: 완료 확인 뒤에는 이 문서를 수정하지 않는다. 이후의 반증, 기술 선택, 상세 설계, 구현 계획과 개발 중 조정은 별도 문서가 소유하며, 이 문서를 바꾸는 대신 어떤 전제나 수단을 계승·기각했는지 연결한다.

이 문서는 이 저장소에서 greenfield로 다시 만드는 **스킬을 만드는 스킬**과, 그것이 만들어 낼 독립적인 target skill의 최초 방향성 기획이다. 구현 명세나 현재 제품의 개량 계획이 아니다. 복잡한 자연어 스킬을 AI가 더 적은 부담으로 더 안정적으로 만들고 사용하게 하려는 최초 문제에서 새 시스템을 정의한다. 기존 프로젝트와의 정확한 관계와 격리 원칙은 1.5와 17절이 소유한다.

> **이 문서의 원점:** 스킬 전체를 더 완벽한 기계로 만드는 것이 아니라, 현재 상황에서 기계가 확실히 계산할 수 있는 부담을 먼저 없애고 AI에게는 목적과 의미 판단이 선명한 최소 작업만 남긴다. 이후의 모든 상태·함수·형식·검사·API는 이 원점을 위한 조건부 수단이다.

## 1. 이 제품은 무엇인가

### 1.1 한 문장 방향

> 방대한 스킬에서 AI가 매번 다시 해석할 필요가 없는 조건·반복·형식·상태·공통 계산은 기계가 미리 처리하고, 현재 작업에서 AI만 판단할 수 있는 최소한의 목적·사실·판단 기준만 전달한다.

목표는 자연어를 제거하는 것이 아니다. 자연어가 맡아야 하는 의미 판단과 기계가 맡을 수 있는 결정 가능한 계산을 분리해, 둘이 각각 가장 잘하는 일을 하게 만드는 것이다.

### 1.2 제품 정체성

이 문서가 기획하는 제품은 **AI가 사용할 복잡한 스킬을 만들고, 그 스킬을 실제 작업에서 작게 읽고 안정적으로 사용하게 하는 범용 저작·사용 기반**이다. 이 저장소에서 기존 구현과 분리해 처음부터 다시 만드는 제품이며, 아래 두 경험을 하나의 연결된 시스템으로 다룬다.

제품의 중심 형태는 **스킬을 만드는 스킬과 그 저작 결과인 독립적인 스킬 패키지**다. 저작 스킬은 사용자 의도를 받아 자연어 판단, 결정 가능한 기계 처리와 출력 형식의 책임을 나누고 target skill을 만든다. 만들어진 target skill은 중앙의 거대한 workflow engine을 이해하거나 호출해야만 쓸 수 있는 종속물이 아니라, 사용하는 AI가 작은 entry에서 시작할 수 있는 독립적인 결과물이어야 한다.

```text
저작 경험:
  사용자와 저작 AI가 목적·판단·기계 규칙·출력 형식을 한 번씩 정의한다.

사용 경험:
  사용하는 AI는 전체 스킬을 통독하지 않고 현재 작업 패킷을 받아 판단·작업하고,
  기계는 관찰·계산·형식·현재성과 다음 작업을 담당한다.
```

제품의 핵심 산출물은 거대한 workflow 정의나 내부 상태 보고서가 아니다. **사람이 유지보수할 수 있는 스킬 원본**과 **AI가 지금 바로 사용할 수 있는 작은 작업 패킷**, 그리고 **실제 결과와 연결된 증거**다.

이 제품은 다음이 아니다.

- Devflow 자체 또는 Devflow 단계들을 범용화한 workflow engine
- AI의 의미 판단과 도메인 작업을 대신하는 결정 엔진
- 모든 자연어를 schema나 DSL로 바꾸는 언어
- host 밖에서 일어난 실제 효과까지 검사 통과만으로 보증하는 통제 시스템
- 테스트 수와 내부 구조의 완전성을 제품 품질로 삼는 framework

### 1.3 전체 시스템 그림

아래는 이번 최초 기획이 그리고 있는 한 장짜리 전체다. 각 상자는 후속 상세 기획에서 이름이나 구현 방식이 바뀔 수 있지만, 정보가 흐르는 방향과 책임 분리는 이 기획의 중심 가설이다.

```text
┌──────────────────────────────────────────────────────────────┐
│ 1. 스킬 원본                                                │
│ 목적·배경 | 판단 기준 | 결정 가능한 규칙 | renderer | 자료 │
└──────────────────────────┬───────────────────────────────────┘
                           │ 저작·검사·build
                           ▼
┌──────────────────────────────────────────────────────────────┐
│ 2. 사용 가능한 스킬 패키지                                 │
│ 작은 entry + 조건부 판단 모듈 + 기계 함수 + 출력 계약       │
└──────────────────────────┬───────────────────────────────────┘
                           │ 사용자 요청 + 현재 workspace 관찰
                           ▼
┌──────────────────────────────────────────────────────────────┐
│ 3. 선택·계산 층                                             │
│ 관련 자료 선택 | 상태·dependency·currentness 계산 | next     │
└──────────────────────────┬───────────────────────────────────┘
                           │ 현재 작업 패킷
                           ▼
┌──────────────────────────────────────────────────────────────┐
│ 4. 사용하는 AI                                              │
│ 의미 판단 | 도메인 작업 | 필요한 사람 결정 요청             │
└──────────────────────────┬───────────────────────────────────┘
                           │ 구조화된 결과
                           ▼
┌──────────────────────────────────────────────────────────────┐
│ 5. 결과화 층                                                │
│ renderer | artifact 기록 | 선택적 host effect | 증거 수집    │
└──────────────────────────┬───────────────────────────────────┘
                           │ 결과·revision·evidence
                           └──────────────▶ 다음 next 계산
```

이 그림에서 기계는 AI 앞뒤의 **결정 가능한 준비와 정리**를 맡는다. AI는 가운데에서 **의미를 판단하고 실제 도메인 작업을 수행**한다. 기계가 의미를 아는 척하거나, AI가 기계가 이미 아는 상태와 형식을 다시 계산하게 만들지 않는 것이 핵심이다.

### 1.4 두 개의 완결된 사용 흐름

제품은 저작과 사용 중 어느 한쪽만 좋아서는 목적을 달성하지 못한다.

```text
스킬을 만들 때
  사용자 의도
    → 저작 AI가 자연어·기계·renderer 책임을 분배
    → 한 사실에 한 정본을 가진 스킬 원본 작성
    → build가 사용 가능한 package와 작은 entry 생성
    → fresh AI가 실제로 사용할 수 있는지 확인

스킬을 사용할 때
  사용자 요청
    → 기계가 workspace를 관찰하고 관련 부분만 선택
    → AI가 작은 작업 패킷으로 판단·작업
    → renderer 또는 도구가 결과를 정확히 기록
    → evidence와 revision으로 다음 작업을 다시 계산
```

저작 흐름의 성공은 package가 생성됐다는 사실이 아니라, 사용하는 AI의 읽기·판단·작업 비용과 실제 결과가 나아진 것이다. 사용 흐름의 성공도 내부 상태가 진행됐다는 사실이 아니라, 사용자가 원한 artifact나 효과가 현재 근거와 함께 남은 것이다.

### 1.5 이 제품, pilot, Devflow와 과거 구현의 관계

| 대상 | 이번 기획에서의 역할 | 제품 정체성에서 제외되는 것 |
| --- | --- | --- |
| **새 스킬 시스템** | 이 저장소에서 greenfield로 만드는 범용 제품 | 현재 Skill Rails 구조의 개량판이라는 전제 |
| **간단한 natural-language pilot** | 가장 작은 수직 흐름과 비용 가설을 가르는 첫 실험 | 범용성 또는 복잡한 workflow 수용의 증명 |
| **Devflow** | 새 시스템으로 만들어 실제 개발 전체를 수행할 첫 완전한 소비자이자 stress case | 새 시스템 자체, core 문법의 원형, 호환해야 할 구조 |
| **기존 Skill Rails·Devflow 구현** | 실패 장면, 실제 필요와 반례를 제공하는 격리된 과거 자료 | 새 architecture·API·상태·test의 기준선 |

관계는 `새 시스템 안에 Devflow가 들어 있다`가 아니라 다음과 같다.

```text
새 범용 스킬 시스템
  ├─ 작은 pilot 스킬을 만들어 핵심 가설을 빠르게 판별
  ├─ Devflow 스킬을 새로 만들어 전체 복잡성을 반증
  └─ 서로 다른 종류의 스킬을 만들어 범용성을 확인
```

따라서 Devflow의 제품 기획, 단계와 도메인 규칙은 Devflow가 소유한다. 이 문서는 Devflow를 만들 수 있게 하는 범용 저작·사용 기반의 목적과 경계만 소유한다.

### 1.6 전체 기획을 붙드는 단일 개념

뒤의 세부 절은 모두 다음 한 흐름을 풀어 쓴 것이다.

```text
스킬 원본
  = 목적 kernel
  + 필요한 때만 읽는 판단 모듈
  + 기계가 실행할 수 있는 계산과 renderer

한 번의 실제 사용
  = 현재 사실 관찰
  → 지금 불필요한 산문·분기·형식 제거
  → AI에게 목적 + 관련 사실 + 판단/행동 하나 전달
  → 결과를 정확히 기록하고 실제 evidence에 연결
  → 다음 호출도 같은 방식으로 다시 계산
```

이 개념의 목표는 **기계화율을 높이는 것**이 아니라 **AI가 매번 읽고 해석하고 기억하고 다시 적어야 하는 총부담을 줄이는 것**이다. 그래서 최상의 시스템은 가장 많은 상태와 규칙을 가진 시스템이 아니라, 다음 네 성질을 동시에 만족하는 시스템이다.

1. **단순하다.** 정상 사용 흐름을 처음 보는 AI가 내부 설계를 배우지 않고도 시작할 수 있다.
2. **깊다.** 결정 가능한 반복은 코드처럼 재사용하고, 의미 판단은 목적과 근거를 잃지 않는다.
3. **유연하다.** 판단 중심 스킬은 산문에 가깝게, 상태·형식 중심 스킬은 필요한 부분만 더 기계화한다.
4. **내구성이 있다.** 새 사례가 생겨도 예외를 core에 계속 넣지 않고 기존 책임의 조합으로 표현한다.

상태, schema, 함수, renderer, 검증과 host 통합은 이 네 성질 중 하나를 실제로 개선할 때만 존재한다. 세부 기능이 이 단일 개념보다 먼저 읽히거나 더 높은 권위를 가지면 기획이 다시 실패한 방향으로 이동한 것이다.

## 2. 이 기획이 태어난 배경과 결정의 계보

이 절은 완성된 설계의 정당화를 나중에 덧붙인 설명이 아니다. 왜 사용자가 이 프로젝트를 시작했고, 왜 기존 방식의 부분 수리가 아니라 전면 재구성을 결정했으며, 이번 기획이 어떤 질문에 답하려는지를 보존한다. 새 세션의 AI는 아래의 배경을 구현 세부보다 낮은 권위의 장식으로 취급하지 않는다. 동시에 이 배경을 “그러므로 현재 기술안만 가능하다”는 결정론적 증명으로 읽지 않는다. 배경은 미래의 새 선택지까지 판단할 기준을 주고, 기술 수단은 계속 반증 가능하게 남긴다.

### 2.1 출발점: Devflow를 자연어 스킬로 만들며 발견한 문제

사용자는 복잡한 개발 workflow인 Devflow를 처음에는 보편적인 자연어 스킬 구조로 만들었다. 이 과정에서 조건문, 반복문, 함수와 공통 자료처럼 코드에서는 짧고 명확하게 표현할 수 있는 로직을 산문으로 설명하려면 수천 줄 규모까지 커질 수 있다는 문제를 직접 경험했다.

이 문제는 문서가 길다는 불편 하나가 아니었다.

1. 조건, 예외, 순서, 반복, 형식과 복구 규칙을 산문으로 풀어 쓰면서 같은 의미가 여러 위치에 흩어졌다.
2. 자연어에는 코드의 함수, 자료형, 호출 관계와 정적 검사 같은 구조적 주소가 약해 한 규칙을 고칠 때 관련 문맥을 다시 찾아 읽고 해석해야 했다.
3. 같은 문장도 모델의 배경지식, 이전 대화, 추론 여유와 working set에 따라 다르게 해석될 수 있었다.
4. AI가 호출할 때마다 방대한 절차를 다시 읽으면서 컨텍스트가 빠르게 커졌고 중요한 목적과 의무가 설명 속에서 희석됐다.
5. 사람이 정기적으로 산문을 다시 맞출 수는 있지만, 복잡한 workflow에서 반복되는 drift와 정합성 확인을 계속 수동 유지보수하는 데 한계가 있었다.

따라서 최초 문제의식은 “AI에게 더 좋은 문장을 써 주자”에 머물지 않았다. **자연어가 맡고 있던 반복 가능한 로직을 코드처럼 구조화하고 재사용하여, 유지보수와 AI의 현재 해석량을 함께 줄일 수 있는가**가 출발 질문이었다.

### 2.2 첫 해결 시도: Skill Rails

사용자는 이 문제를 해결하기 위해 스킬을 만드는 스킬인 Skill Rails를 기획했다. 의도는 자연어 파일을 단순히 나누고 번호를 붙이는 데 그치지 않았다.

- 필요한 파일만 선택적으로 읽는 tree 구조를 만든다.
- 조건, 반복, 공통 계산, 형식과 상태 전이를 기계가 소유하게 한다.
- AI가 절차를 어겼을 때 기계가 발견하거나 바로잡을 수 있게 한다.
- 스킬 저작과 결과를 더 균일하고 신뢰할 수 있게 만든다.
- 동일한 로직을 산문 여러 곳에 반복하지 않고 함수처럼 재사용한다.

사용자는 목적과 목표를 강하게 제시하고, 구체적인 기획과 개발 과정의 상당 부분을 AI에게 맡겨 이 시도를 진행했다. Devflow를 실제 소비 사례로 만들면서 필요한 지원이 없다는 피드백이 나올 때마다 Skill Rails를 고도화하고 배포한 것도 이 목적을 완성하기 위한 과정이었다.

그러나 이 과정은 점차 “AI가 실용적으로 잘 쓰는가”보다 “기계가 더 많은 상황을 표현하고 검사할 수 있는가”를 해결하는 방향으로 이동했다. 하나의 실패를 막는 guard, 상태, 입력 규약, 검사와 복구 설명이 추가되고, 그 추가물을 사용하기 위한 산문과 다른 검사가 다시 필요해졌다.

### 2.3 전환점: 사용자가 내린 실패 판단

사용자는 약 20일 동안 실제 사용과 반복 시험을 거친 뒤, 기존 Skill Rails와 그것으로 만든 Devflow를 현재 목적에 비추어 실패로 판단했다. 이 판단의 근거는 모든 기능이 동작하지 않았다는 뜻이 아니다.

- AI는 여전히 예상과 다르게 행동했고 실제 목표 흐름의 신뢰도가 충분히 높아지지 않았다.
- 시스템을 읽고 호출하고 값을 전달하고 복구하는 비용이 지나치게 커졌다.
- AI가 자연어 의미를 판단해 기계 입력값을 만든 뒤 다시 다음 행동을 조립해야 하는 경우, 기계는 판단 부담을 제거하지 못하고 중간 절차만 추가했다.
- 문제를 막기 위해 구조와 검사를 늘렸지만 원래 의도했던 산문·컨텍스트·유지보수 비용은 충분히 줄지 않았다.
- 내부 구조와 테스트의 완성도가 실제 AI 행동과 사용자 결과보다 앞서기 시작했다.

저장소의 관찰도 이 경험과 같은 방향을 가리킨다. Devflow에서는 모든 소비자가 읽는 공통 절이 전체 규칙 정본의 69%였고, 상태가 있는 저장소의 세션 진입 비용은 약 148,000 byte, 대략 37k token으로 측정됐다. 588개의 테스트를 매 변경마다 실행했지만 독립 논리 검토가 찾은 네 결함을 그 suite가 하나도 잡지 못했으며, 실제 완료 gate는 열여덟 release 동안 실행되지 않았다. 이 수치는 각각 sibling repository의 `../devflow/docs/backlog.md`와 `../devflow/CHANGELOG.md`에 기록되어 있다.

이 관찰은 기계화가 불가능하다는 증명이 아니다. **기계화한 내부 구조의 양과 실제 AI 사용성·행동 신뢰성 사이에 자동적인 비례 관계가 없었다**는 증거다.

### 2.4 전면 재구성을 촉발한 사용자의 질문

사용자가 다시 연 질문은 “현재 Skill Rails를 어떻게 고칠까”가 아니었다.

```text
- 애초의 기계화 의도는 유의미했는가, 아니면 불필요한 노력이었는가?
- 잘 쓴 산문을 파일과 tree로 나누고 사람이 가끔 drift를 교정하는 것으로 충분하지 않았는가?
- AI가 의미를 판단해 값을 기계에 넣어야 한다면, 그 경유가 실제 산문과 컨텍스트를 줄이는가?
- 조건·반복·함수 같은 개념을 AI 관점에서 기술적으로 어디까지 덜어 낼 수 있는가?
- 상태는 언제 재개와 동시성에 도움이 되고, 언제 거대한 관리 체계가 되는가?
- 정확한 쓰기와 template은 AI가 외울 필요 없이 기계가 맡을 수 있는가?
- 테스트는 실제 결과의 정합성을 확인하는가, 아니면 시스템을 경직시키는 점수표가 되었는가?
```

사용자가 언급한 중개노트 사례는 단순한 자연어 중심 구조도 사람이 한 달에 한 번가량 drift를 바로잡는 정도로 실용적으로 운영될 수 있음을 보여 주는 경험적 대조다. 이것은 모든 복잡한 스킬에 산문만으로 충분하다는 증명은 아니지만, 기계화가 언제나 더 낫다는 전제를 무너뜨린다. `../devflow/tests/natural-language-pilot`도 같은 질문을 더 작은 개발 흐름에서 비교하기 위해 만들어졌으며, 아직 실제 우열을 증명한 결과가 아니라 기준안이다.

### 2.5 결정의 소유권과 현재 범위

기존 프로젝트를 대대적으로 리뉴얼하고 처음부터 다시 시작하기로 한 결정은 AI가 자동으로 도출한 기술 결론이 아니라 **사용자가 실제 사용 경험을 바탕으로 내린 제품 결정**이다.

현재 확정된 결정은 다음과 같다.

- 기존 Skill Rails와 Devflow의 계획·architecture·API·상태 기계·호환 계약을 유지하면서 개선하지 않는다.
- 기존 구현 대부분은 새 실행·build·test 경로와 분리된 백업 영역에 보존한다.
- 과거 구현은 실패 장면과 실제 필요를 발견하는 자료로 사용하지만 새 구조를 선점하지 못한다.
- 새 시스템은 가장 합리적인 구조를 빈 기준선에서 세우고 작은 수직 흐름부터 다시 구현한다.
- 간단한 pilot을 첫 실험으로 사용하지만, 실제 Devflow의 복잡성을 첫 완전한 소비자 목표로 삼는다.
- Devflow를 수용하되 Devflow만을 위한 시스템을 만들지 않는다.

AI는 이 결정의 목적을 더 잘 실현할 수단을 제안하고 반증할 수 있다. 그러나 기존 구현을 보존하는 편이 쉽다는 이유로 점진 개선으로 되돌리거나, 반대로 과거의 유효한 필요와 관찰까지 무가치하다고 폐기할 권한은 없다.

### 2.6 이번 기획이 내린 해석

이번 검토가 내린 핵심 해석은 **최초 의도는 유의미했지만 기계화의 책임 경계와 제품 성공 기준이 잘못 확장되었다**는 것이다.

- 파일 tree와 선택적 읽기는 여전히 유효하다.
- 같은 입력에서 같은 답을 낼 수 있는 경로·형식·순서·dependency·currentness·renderer는 기계화 가치가 있다.
- 목적, 가치 충돌, 새로운 반례, 문제 정의와 충분성 판단은 AI와 사람의 자연어 영역이다.
- AI가 판단한 값을 전달받는 기계도 후속 계산·분기·렌더링·현재성 관리를 실제로 제거한다면 가치가 있다.
- 반대로 AI가 동일한 판단과 조립을 계속 수행해야 한다면 그 기계는 제거 대상이다.
- 신뢰성은 구조 검사 하나가 아니라 의미·전달·행동·실제 효과의 서로 다른 증거로 판단해야 한다.

따라서 새 방향은 산문으로 회귀하거나 기계화를 더 완성하는 양자택일이 아니다. **자연어와 기계를 AI의 실제 작업 흐름에서 다시 배치하고, 현재 상황에 필요한 잔여 판단만 AI에게 전달하는 부분 컴파일 구조**다.

이 배경에 포함된 내용의 권위는 서로 다르다.

| 구분 | 현재 내용 | 이후 취급 |
| --- | --- | --- |
| 사용자 경험 | 예상 밖 AI 행동, 높은 사용 비용, 반복 수리에도 목적 미달 | 원문을 보존하고 새 관찰이 있으면 범위를 더 정확히 한다 |
| 저장소 관찰 | context 규모, 공통 읽기 비율, 테스트가 놓친 결함과 미실행된 실제 gate | 같은 조건의 최신 실측으로 갱신하거나 반박할 수 있다 |
| 사용자 결정 | 기존 구조를 기준선으로 고치지 않고 greenfield로 재구성 | 사용자의 새 명시적 결정 없이는 바꾸지 않는다 |
| 기획 해석 | 실패의 중심은 기계화 자체보다 책임 확장과 잘못된 성공 증거였다 | 경쟁 해석과 실제 사용 비교로 반증할 수 있다 |
| 잠정 수단 | 부분 컴파일, 작은 작업 패킷, `next()`, 최소 상태, renderer | 더 단순하고 효과적인 수단이 확인되면 교체한다 |

따라서 배경을 보존한다는 것은 현재 기술안을 그대로 따르라는 뜻이 아니다. 새 선택이 최초 문제와 사용자 결정을 더 잘 만족한다면 채택할 수 있지만, 무엇을 더 잘 해결하며 어떤 기존 부담을 없애는지 설명해야 한다.

### 2.7 과거 실패에서 보존할 사실

과거 시도는 기계화가 불가능하거나 기존 작업이 무가치하다는 것을 증명하지 않았다. 기존 Skill Rails와 Devflow는 어떤 능력이 실제로 필요해지는지, 복잡한 개발 workflow가 어디까지 확장되는지, 어떤 접근이 그 필요를 해결하지 못했는지를 발견한 중요한 자산이다.

- 경로, 형식, 상태값, 순서, dependency, hash와 같이 같은 입력에서 같은 답을 낼 수 있는 규칙은 코드로 옮겼을 때 분명한 가치가 있다.
- 기계가 의미 판단과 실제 AI 행동까지 통제할 수 있다고 범위를 넓히면, 입력 규약·상태 기계·검사·복구 매뉴얼이 증식하고 종단 사용자 결과는 오히려 멀어질 수 있다.
- 새로운 프로젝트 기획뿐 아니라 기존 프로젝트 역산, 설계, 작업 분해, 구현, 검증, 재개, 지식 보존과 여러 AI의 협업까지 한 흐름에서 다룰 필요가 실제로 존재한다.
- 실패한 것은 이러한 필요 자체가 아니라, 필요를 하나씩 막는 과정에서 기계와 산문이 비대해지고 AI가 실제로 사용하는 흐름보다 내부 체계의 완성도가 우선된 방식이다.

따라서 과거 구현은 계승할 정답은 아니지만 폐기할 지식도 아니다. 과거에 필요했던 능력은 새 방향과 새 책임 경계에서 다시 구현될 수 있다. 과거의 분류, 문법, 파일 배치와 해결 방식을 보존하는 것이 아니라, 새 시스템의 작은 primitive로 같은 실제 필요를 더 단순하게 해결해야 한다.

### 2.8 문제 주장

복잡한 스킬을 사용하는 AI가 현재 작업과 무관한 절차 산문까지 반복해서 읽고, 기계적으로 계산할 수 있는 분기와 형식까지 매번 재해석해야 하므로 컨텍스트 비용, 해석 편차와 유지보수 비용이 커진다. 이를 기계화하려는 시스템도 AI가 실제로 덜 수행하는 일이 무엇인지보다 내부 표현과 통제를 늘리면 같은 문제를 더 복잡한 형태로 반복한다.

### 2.9 원하는 변화

- 스킬 전체가 커져도 한 번의 작업에서 AI가 읽는 안내는 작게 유지된다.
- 동일 입력의 동일 결과는 자연어 기억이 아니라 코드와 데이터 구조가 계산한다.
- AI는 문제의 의미, 가치 충돌, 새로운 반례와 사용자 의도처럼 실제 판단이 필요한 일에 집중한다.
- 정확한 문서 형식은 AI가 기억해 재현하지 않고 기계가 생성한다.
- 세션이 중단되거나 여러 터미널이 동시에 작동해도 전체 스킬을 다시 읽지 않고 현재 작업을 복구할 수 있다.
- 검사가 통과했다는 사실과 AI가 잘 행동했다는 사실과 실제 문제가 해결됐다는 사실을 구분한다.
- 사용자는 내부 기계를 운영하는 대신 원하는 스킬과 결과를 설명하는 데 집중한다.

### 2.10 새 세션의 독해 계약

이 문서는 다음 작업을 자동으로 정하는 실행 상태 파일이 아니다. 새 세션의 AI는 사용자의 새 지시를 받아야 한다. 다만 이 문서 하나만 읽고도 다음 배경은 복원할 수 있어야 한다.

1. 이 프로젝트는 자연어 스킬의 유지보수·컨텍스트·해석 편차를 줄이려는 문제에서 시작했다.
2. 사용자는 그 문제를 해결하려 Skill Rails를 만들었지만, 실제 사용 뒤 현재 구현을 실패로 판단하고 greenfield 재구성을 결정했다.
3. 실패한 것은 모든 기계화와 과거의 필요가 아니라, 기계 책임의 과도한 확장과 내부 완성도를 실제 효과로 본 접근이다.
4. 새 기획의 중심은 부분 컴파일이며, AI의 의미 판단을 없애는 것이 아니라 현재 필요한 판단만 남기는 것이다.
5. 간단한 pilot은 최초 판별 실험이고 Devflow는 첫 완전한 소비자이지 제품 자체가 아니다.
6. 기존 구현은 후행 반증 자료이며 새 architecture의 기준선이 아니다.
7. 고정 목적과 사용자의 결정은 잠정 수단보다 높은 권위를 가진다.
8. 새 지시가 이 배경과 충돌하는 것처럼 보이면 AI는 조용히 어느 한쪽을 바꾸지 않고 충돌 지점과 필요한 결정을 사용자에게 제시한다.

새 세션의 AI가 위 내용을 설명하지 못하면, 세부 기능을 많이 읽었더라도 이 최초 기획을 충분히 이해한 것이 아니다.

## 3. 고정 목적과 잠정 수단

이 문서를 동결한 뒤에도 고정 목적과 잠정 수단을 구분한다. 최초 기획을 보존한다는 이유로 당시의 기술 가설까지 영구 불변식으로 만들지 않는다.

### 3.1 고정 목적

1. **AI의 실제 사용 비용을 줄인다.** 저장된 전체 문서 크기가 아니라 한 작업에서 읽고 해석하고 왕복해야 하는 총비용을 줄인다.
2. **AI가 해야 할 판단을 선명하게 만든다.** 기계가 판단을 대신하는 척하지 않고, 현재 필요한 판단의 입력·기준·출력을 좁힌다.
3. **결정 가능한 로직은 한 번만 구현한다.** 조건, 반복, 형식과 공통 계산을 산문 여러 곳에 복제하지 않는다.
4. **실제 작업 결과를 개선한다.** 구조·테스트·코드의 완성도 자체를 제품 성공으로 삼지 않는다.
5. **가장 작은 충분한 시스템을 유지한다.** 새 장치는 제거하거나 단순화하는 기존 비용이 있을 때만 들어간다.
6. **AI가 사용하기 쉬운 인터페이스를 우선한다.** 기계 내부의 완전성보다 AI가 직관적으로 다음 행동을 얻고 결과를 제출하는 흐름을 우선한다.
7. **범용 core와 개별 스킬의 도메인을 분리한다.** 여러 스킬에서 반복되는 저작·선택·계산·렌더링·증거 기능만 core가 소유하고, 한 스킬의 단계·판단·용어를 범용 문법으로 일반화하지 않는다.
8. **실패한 구조를 점진 개선의 기준선으로 삼지 않는다.** 새 시스템은 빈 구조에서 시작하며, 기존 Skill Rails와 Devflow에 대한 호환·이식·부분 보존을 기본 요구로 두지 않는다.

### 3.2 잠정 수단

다음은 현재 가장 합리적인 가설이지만 후속 검증에서 교체할 수 있다.

- 스킬을 부분 컴파일하는 구조
- 기계 함수, 렌더링 함수, 판단 함수의 구분
- `next` 중심의 단순 실행 인터페이스
- artifact에서 상태를 우선 재계산하고 최소 조정 상태만 보존하는 방식
- 구조화된 내용 입력과 기계 렌더링을 결합한 쓰기 방식
- 기준안과 변경안을 비교하는 행동 검증 방식
- 구체적인 파일 구조, 구현 언어, schema 형식, 저장소 위치와 host adapter

### 3.3 원점 보존 게이트

후속 검증과 개발은 잠정 수단을 자유롭게 반증하고 바꿀 수 있다. 그러나 구현 편의, 이미 만든 코드, test 통과, 일정과 새로운 기능의 매력 때문에 최초 목적을 조용히 바꾸면 안 된다.

모든 큰 기획 변경, 새 core primitive와 검증 결과를 받아들이기 전에 다음을 다시 쓴다.

```text
최초 사용자 문제:
  방대한 자연어 로직의 유지보수·재해석·컨텍스트 비용과 행동 편차

보존할 변화:
  기계가 확실히 계산할 부담은 제거하고 AI의 의미 판단은 더 작고 선명하게 만든다.

이번 제안이 실제로 제거하는 것:
  어떤 반복 산문, AI 추론, 형식 기억, 왕복, 복구 또는 실패가 사라지는가?

이번 제안이 새로 요구하는 것:
  AI가 배워야 할 개념, 입력해야 할 값, 읽을 context, 상태, 검사와 복구 비용은 무엇인가?

종단 확인:
  내부 구조가 아니라 실제 target skill을 사용하는 AI와 사용자 결과가 어떻게 좋아지는가?
```

다음 중 하나이면 개선으로 승격하지 않는다.

- 기계가 이미 알 수 있는 값을 AI에게 다시 계산·입력하게 한다.
- 새로운 장치가 없애는 부담보다 그 장치를 이해·운영·복구하는 부담이 크다.
- 의미·목적 판단을 형식 통과 여부로 바꾸거나, AI 행동 증거를 내부 test로 대신한다.
- 단순한 산문 기준안과 비교하지 않은 채 기계 구조의 완성도를 높인다.
- Devflow 한 사례의 단계·용어·예외를 범용 core의 필수 개념으로 만든다.
- 세부 기능을 지키기 위해 작은 entry와 현재 작업 패킷이 다시 커진다.

검증이 부분 컴파일, `next()`, 상태나 renderer를 반증하면 그 수단은 버릴 수 있다. 반대로 검증 결과가 최초 목적 자체를 바꿔야 한다고 보이면 AI가 자동으로 수정하지 않고 사용자에게 목적 결정으로 돌려보낸다. 이 문서의 “동결”은 기술 가설을 신성화하는 장치가 아니라 이 원점이 구현의 편의에 묻히지 않게 하는 장치다.

## 4. 핵심 가설: 스킬의 부분 컴파일

### 4.1 정의

부분 컴파일은 전체 스킬 원본과 현재 관찰 가능한 상태를 결합해, 지금 필요하지 않은 분기·절차·형식 설명을 기계가 먼저 제거하고 AI가 수행해야 하는 잔여 판단과 행동만 만드는 것이다.

```text
전체 스킬 원본
  ├─ 목적과 배경
  ├─ 조건과 분기
  ├─ 반복과 dependency
  ├─ 공통 계산
  ├─ 문서 형식
  ├─ 상태와 현재성
  └─ 의미 판단 기준
          │
          ▼
현재 프로젝트 사실과 결합
          │
          ▼
기계가 미리 계산
  - 현재 단계 결정
  - 관련 없는 분기 제거
  - 이미 충족된 의무 제거
  - 작업 대상과 순서 계산
  - 관련 자료와 판단 모듈 선택
  - 출력 schema와 renderer 준비
          │
          ▼
AI가 받는 잔여 작업
  - 현재 목적
  - 관련 사실
  - 판단 또는 행동 하나
  - 그 판단에 필요한 기준
  - 제출할 내용의 구조
```

### 4.2 줄이는 것은 정보가 아니라 현재 해석량이다

원본의 정보는 코드, schema, renderer, 판단 모듈과 목적 문서에 계속 존재한다. 줄여야 하는 것은 저장된 총 byte가 아니라 한 invocation에서 AI가 다시 해석해야 하는 양이다.

수천 줄이 모두 현재 판단에 필요한 고유한 도메인 지식이라면 기계화로 없앨 수 없다. 이때는 작업 분해, 조건부 검색, 전문 판단 모듈, 요약 artifact가 필요하다. 반대로 수천 줄의 상당 부분이 절차·형식·반복·예외 나열이라면 기계가 실행해 AI의 working set에서 제거할 수 있다.

### 4.3 성공한 부분 컴파일의 출력

AI에게 주는 기본 출력은 내부 상태 기계의 dump가 아니라 작은 현재 작업 패킷이다.

```yaml
goal: 사용자가 얻으려는 현재 결과

current_task:
  id: 안정적인 작업 식별자
  action: 지금 수행할 행동 하나

known:
  - 기계가 관찰했거나 명시적으로 결정된 관련 사실

judgment_needed:
  question: AI만 답할 수 있는 질문 하나
  criteria:
    - 이 판단에만 필요한 기준

resources:
  - 현재 작업에 필요한 파일이나 요약

return:
  - AI가 제출할 의미 필드

completion:
  - 이번 작업 단위가 끝났다고 볼 관찰 가능한 조건
```

내부 구현 용어, 사용하지 않는 분기, 전체 trace와 미래 단계는 기본 출력에 넣지 않는다.

## 5. 자연어와 기계의 경계

### 5.1 자연어가 소유할 것

- 제품과 작업의 목적
- 사용자 가치와 우선순위
- 의미가 충돌할 때의 판단 기준
- 새로운 반례가 중요한지에 대한 해석
- 문제 정의, 설계 선택과 작업 분해의 타당성
- 기계가 관찰할 수 없는 현실 맥락
- 왜 이 규칙이 존재하는지에 대한 짧은 이유

### 5.2 기계가 소유할 것

- 파일과 artifact의 존재, 경로, hash와 currentness
- 필수 필드, 허용 값, 자료형과 exact format
- ID 생성, dependency graph, 순환과 실행 가능 항목
- 정렬, 필터, 집계, 반복, 중복 제거와 정규화
- 이미 명시된 상태에서의 결정적 분기
- renderer를 통한 문서 생성
- 승인이나 검증 결과가 어떤 원본 revision에 결합됐는지
- 실행 가능한 명령의 실제 exit status와 수집 가능한 출력

### 5.3 경계에 있는 것

다음은 의미 판단과 기계 처리를 결합한다.

- AI가 성공 기준을 제안하고 기계가 누락·형식·중복을 검사한다.
- AI가 작업 분해를 제안하고 기계가 ID·dependency·순환·카드 수를 검사한다.
- AI가 검증 방법을 선택하고 기계가 실행·결과 수집·현재성 연결을 담당한다.
- AI가 결과의 의미를 판정하고 기계가 그 판정이 어떤 evidence를 근거로 했는지 보존한다.

### 5.4 기계화 입장 조건

새 기계 요소는 다음에 모두 답할 수 있을 때만 추가한다.

1. 어떤 반복되는 산문·수동 계산·현재 실패를 제거하는가?
2. 같은 입력에서 같은 결과를 계산할 수 있는가?
3. AI가 이 규칙을 읽지 않아도 결과를 이용할 수 있는가?
4. 구현·설명·복구·검증 비용의 합이 제거하는 비용보다 작은가?
5. 잘못됐을 때 어느 한 소유자에서 제거하거나 되돌릴 수 있는가?

한 조건이라도 충족하지 못하면 자연어 판단으로 남기거나 후속 관찰로 보류한다.

## 6. 세 종류의 재사용 함수

### 6.1 기계 함수

동일 입력에서 동일 결과를 만드는 일반 코드다.

```text
normalizeId()
validateRequiredFields()
findRunnableUnits()
detectDependencyCycle()
checkArtifactFreshness()
compareChangedFilesToScope()
selectRelevantModules()
collectCommandResult()
```

이 기능의 의미를 여러 스킬 산문에 반복하지 않는다. 기계 함수와 테스트가 소유하고 AI는 필요한 결과와 실패 이유만 받는다.

### 6.2 렌더링 함수

AI가 제출한 의미 필드를 정확한 문서나 메시지로 만든다.

```text
구조화된 내용
  → schema 검사
  → renderer
  → preview 또는 diff
  → 원자적 쓰기
  → 생성 결과와 입력 revision 기록
```

AI는 Markdown 제목 순서, 표 구문, 구두점, 반복 item 형식과 누락 방지 규칙을 기억할 필요가 없다.

### 6.3 판단 함수

코드가 직접 답할 수 없지만 매번 전체 스킬을 읽힐 필요도 없는 작은 AI 판단 모듈이다.

```yaml
id: decompose-work
purpose: 승인된 성공 기준을 독립 검증 가능한 작업으로 나눈다
input:
  - product_brief
  - relevant_code_summary
criteria:
  - 한 작업이 하나의 검증 가능한 결과를 가지는가
  - dependency가 실제 구현 순서에 필요한가
  - 분해 비용이 독립 검증의 이득보다 큰가
output:
  - work_units
  - dependencies
  - reason
```

판단 함수는 모델이 실행하는 작은 의미 함수다. 기계가 현재 조건에 맞는 판단 함수만 선택하고, 반환된 판단은 관찰 사실과 구분해 저장한다.

## 7. 조건, 반복과 공통 로직의 실행 모델

### 7.1 조건의 세 출처

| 조건 | 예 | 처리 |
| --- | --- | --- |
| 기계 관찰 | 파일 존재, hash 변경, exit code, 필드 누락 | 기계가 직접 계산 |
| 명시 결정 | 사용자 승인, 선택한 범위, 허용한 효과 | 결정 주체와 대상 revision을 함께 저장 |
| 의미 판단 | 계획이 충분한가, 반례가 중대한가 | 필요한 판단 모듈만 AI에게 전달 |

의미 판단값을 관찰 사실로 승격하지 않는다. 특히 높은 위험의 행동은 AI 판단값만으로 허용하지 않고 명시적 사람 결정이나 실제 관찰을 요구한다.

### 7.2 반복

기계는 반복 대상과 완료 상태를 관리한다.

```js
for (const criterion of acceptanceCriteria) {
  if (!hasCurrentEvidence(criterion)) {
    return createVerificationTask(criterion);
  }
}
return complete();
```

AI는 전체 목록을 기억하지 않고 현재 항목 하나를 처리한다. 항목별 의미 작업은 AI가 수행하지만 열거, 중복 제거, 완료 추적과 다음 항목 선택은 기계가 맡는다.

### 7.3 협력형 반복

일반적인 파일 기반 스킬에서는 기계가 모델을 직접 반복 호출할 수 없을 수 있다. 기본 모델은 다음의 협력형 반복이다.

```text
AI → next() → 현재 작업 하나
AI → 작업 수행 및 의미 결과 제출
AI → next() → 갱신된 현재 작업 하나
```

한 번의 호출에 전체 미래 계획을 전달하지 않는다. `next()`는 현재 관찰에서 다시 계산되며, 대화 기억을 workflow 상태로 사용하지 않는다.

## 8. 상태의 위치와 역할

상태는 유용할 수 있지만 항상 필요한 중앙 상태 기계가 아니다. 목표는 상태를 많이 저장하는 것이 아니라 다음 invocation이 전체 산문과 이전 대화를 다시 읽지 않아도 되게 하는 것이다.

### 8.1 상태의 세 층

#### A. artifact에서 다시 계산 가능한 상태

가장 먼저 사용한다.

- 어떤 문서가 존재하는가
- 어떤 revision을 기준으로 작성됐는가
- 어떤 작업이 완료됐는가
- 현재 검증이 어느 변경에 대응하는가
- dependency가 만족됐는가

이 사실은 별도 상태 파일에 복제하지 않고 artifact와 repository에서 계산한다.

#### B. invocation-local 임시 상태

한 번의 호출 안에서만 필요한 값이다.

- 현재 선택한 작업
- 이번 호출에서 수집한 파일
- 아직 제출하지 않은 renderer 입력
- 현재 오류와 재시도 정보

호출이 끝나면 버릴 수 있다. 장기 상태에 넣지 않는다.

#### C. 최소 durable 조정 상태

세션 중단, 여러 터미널, 장기 작업 때문에 artifact만으로 복구할 수 없을 때만 저장한다.

```yaml
task_id: 독립 작업 식별자
unit_id: 현재 작업 단위
revision: 낙관적 동시성 번호 또는 fingerprint
status: open | waiting | completed | superseded
basis:
  - 판단과 작업이 근거한 artifact revision
open_decision:
  - 아직 사람 또는 AI의 판단이 필요한 항목
outputs:
  - 생성된 artifact reference
updated_at: 기록 시점
```

여기에는 목적 문서나 판단 근거의 본문을 다시 복사하지 않는다. 상태는 의미 정본이 아니라 현재 작업의 좌표다.

### 8.2 여러 터미널과 세션

전역 `current session`이나 하나의 공유 현재 단계를 두지 않는다.

- 상태는 workspace·skill·task 단위로 분리한다.
- 서로 다른 작업은 서로 다른 `task_id`를 사용한다.
- 갱신에는 자신이 읽은 `revision`을 함께 제출한다.
- revision이 달라졌으면 덮어쓰지 않고 새 사실에서 `next()`를 다시 계산한다.
- 장기 lock은 사용하지 않는다. 원자적 write 순간에만 짧은 잠금이나 compare-and-swap을 사용한다.
- 같은 artifact를 두 작업이 수정하려 하면 자동 병합하지 않고 충돌 좌표를 반환한다.
- 끝난 상태는 현재 정본으로 계속 운반하지 않고 요약하거나 폐기한다.

이 방식은 여러 터미널이 하나의 거대한 상태 파일을 서로 덮어쓰는 실패를 피하면서, 중단 뒤 재개에 필요한 좌표는 보존한다.

### 8.3 상태를 도입하지 않을 조건

- 한 invocation에서 끝나는 작업
- artifact 존재와 내용만으로 현재 위치를 계산할 수 있는 작업
- 상태 저장·복구 설명이 원래 절차보다 긴 작업
- 상태가 실제 행동을 바꾸지 않고 보고용으로만 중복되는 작업

## 9. 쓰기와 템플릿

### 9.1 기본 원칙

정확한 틀이 필요한 결과를 AI가 직접 완성 문서로 재현하게 하지 않는다. AI는 의미 내용을 구조화해 제출하고, 기계가 최종 형식을 소유한다.

```text
AI가 내용 필드 제출
  → schema가 필수 값과 형식을 검사
  → renderer가 완성 문서 생성
  → 필요하면 AI 또는 사람이 preview 확인
  → 원자적으로 기록
```

### 9.2 AI가 받아야 할 것

AI는 전체 template이 아니라 다음을 받는다.

- 각 필드의 의미
- 필수 여부
- 자유 산문인지 목록인지 선택값인지
- 판단에 필요한 예시 한두 개
- 현재 입력으로 채울 수 없는 필드를 `unknown`으로 남기는 방법

### 9.3 기계가 맡을 것

- 제목과 절 순서
- 표와 목록 형식
- ID와 timestamp
- 반복 item 렌더링
- 구두점과 exact token
- 누락·중복·알 수 없는 필드 거부
- 기존 문서의 보존해야 할 영역
- 생성 전후 diff와 입력 revision 연결

### 9.4 자유 산문을 허용할 것

모든 문서를 form으로 만들지 않는다. 문제의 배경, 설계 근거, 복잡한 판단과 설명은 자유 산문 block으로 받을 수 있다. 기계는 그 block의 존재와 위치를 관리하지만 내용의 의미를 제한된 enum으로 축소하지 않는다.

### 9.5 부분 수정

기존 문서를 바꿀 때 전체 파일을 AI가 다시 쓰지 않는다.

- 구조화된 slot은 slot 단위로 교체한다.
- 자유 산문은 명시된 section 단위로 수정한다.
- 수정 전 basis와 수정 후 diff를 제공한다.
- 정본이 아닌 생성 영역은 renderer만 쓴다.
- 서로 다른 writer가 같은 section을 건드리면 충돌로 중단한다.

## 10. AI 중심 인터페이스

### 10.1 기본 명령 개념

AI가 기억해야 할 공개 동작은 가능한 한 작게 유지한다.

```text
next(project, optional task)
submit(task, result)
render(artifact, content)
inspect(optional target)
```

실제 구현에서 더 적은 명령으로 합칠 수 있다면 합친다. 내부적으로 여러 단계가 있더라도 AI에게 그 순서를 매뉴얼로 요구하지 않는다.

### 10.2 자동 관찰 우선

기계가 알 수 있는 값을 AI에게 입력하라고 요구하지 않는다.

- 경로, hash, 현재 branch, 파일 존재와 command result는 기계가 읽는다.
- 이전 출력과 현재 revision의 관계도 기계가 계산한다.
- AI에게는 목적, 의미, 선택과 이유처럼 기계가 알 수 없는 것만 묻는다.

### 10.3 한 번에 하나의 지적 과업

하나의 작업 패킷은 원칙적으로 하나의 주된 판단 또는 행동만 요구한다. 기계적 준비, 후처리와 기록을 같은 응답에서 AI에게 동시에 떠넘기지 않는다.

### 10.4 오류 표현

오류는 내부 코드나 상태 이름보다 다음을 먼저 말한다.

```text
무엇을 하려 했는가
어떤 현재 사실 때문에 진행할 수 없는가
AI·사람·기계 중 누가 무엇을 제공해야 하는가
다시 실행할 최소 동작은 무엇인가
```

### 10.5 AI 사용 비용 예산

기계 내부의 코드량만으로 단순성을 평가하지 않는다. 후속 상세 기획은 대표 작업마다 다음 비용을 측정하고, 새 기능이 어느 비용을 줄이고 늘리는지 함께 보여야 한다.

- 항상 읽는 entry와 목적 kernel의 byte 또는 token
- 현재 조건에서만 읽는 판단 모듈과 resource의 양
- 현재 작업 패킷의 크기
- 한 작업 단위를 끝내기 위한 tool 왕복 수
- AI가 기계 내부 값을 옮겨 적어야 하는 횟수
- 사람에게 묻는 횟수와 그 질문의 정보량
- 세션 중단 뒤 복구에 필요한 호출과 읽기 수
- durable 상태의 크기와 충돌 해결 단계
- 잘못된 결과를 고치기 위해 수정해야 하는 정본의 수

정확한 상한은 후속 실측으로 결정한다. 그러나 새 기능이 이 비용 중 무엇을 개선하는지 설명하지 못하면, 내부 구현이 정교하더라도 AI 중심의 개선으로 보지 않는다.

## 11. 실행 권한에 따른 보장 경계

### 11.1 파일 기반 스킬과 동봉 도구

가능한 것:

- 현재 작업 계산
- 조건부 산문 선택
- schema 검증과 문서 렌더링
- dependency와 currentness 검사
- 결과와 evidence의 관계 확인

보장할 수 없는 것:

- AI가 도구를 호출하지 않고 직접 행동하는 것을 완전히 차단
- 모든 shell·파일·외부 메시지 효과를 가로채기
- AI가 작업 패킷을 정확히 이해하고 따랐다는 사실

이 경계에서는 시스템을 강제기라고 부르지 않는다. 압축기, 안내자, renderer와 validator다.

### 11.2 모든 효과가 통과하는 도구 API

AI가 파일·명령·메시지 작업을 통제된 API를 통해 수행하는 환경에서는 다음을 강제할 수 있다.

- 승인 전 write 거부
- 범위 밖 경로 쓰기 거부
- dependency 미완료 작업 거부
- 오래된 검증의 재사용 거부
- schema와 template 강제
- 실행 결과의 자동 evidence 연결

### 11.3 host hook 또는 sandbox

host가 모든 tool effect를 가로채는 경우 가장 강한 실행 통제가 가능하다. 그러나 이는 휴대 가능한 일반 스킬의 보장이 아니며 별도 adapter와 권한 모델의 책임이다.

제품은 현재 host가 어느 수준을 제공하는지 감지하고, 관찰하거나 강제하지 못한 효과를 성공으로 표현하지 않는다.

## 12. 테스트와 검증

### 12.1 테스트의 목적

테스트는 기계의 완성도를 점수화하기 위한 것이 아니다. 다음 결정을 바꿀 수 있는 실패를 발견하기 위한 것이다.

```text
기계가 동일 입력에서 동일 결과를 만드는가
renderer가 약속한 구조를 만드는가
현재 작업 패킷이 AI의 실제 행동을 개선하는가
그 행동이 사용자가 겪던 문제를 줄이는가
```

### 12.2 네 검증 면

| 검증 면 | 질문 | 적절한 증거 |
| --- | --- | --- |
| 의미 | 원본이 요구하는 행동과 판단이 목적에 맞는가 | 사람·AI의 원문 검토와 반례 |
| 전달 | 필요한 정보가 현재 작업 패킷과 결과물에 손실 없이 도달하는가 | 생성 비교, schema, renderer 검사 |
| 행동 | 깨끗한 AI가 실제로 원하는 다음 행동을 하는가 | fresh-agent 실행과 transcript |
| 효과 | 그 행동이 실제 사용자 문제를 줄였는가 | 결과물과 실제 workflow 관찰 |

한 면의 통과를 다른 면의 성공으로 부르지 않는다.

### 12.3 기계 테스트

다음처럼 결정적인 부분만 깊게 검사한다.

- pure function 단위 테스트
- schema positive·negative·boundary 사례
- dependency와 currentness의 대표 반례
- renderer golden 또는 구조 검사
- 동시 갱신과 stale revision 거부
- 동일 입력의 결정성

모든 조합을 무조건 생성하지 않는다. 높은 위해를 가진 결합, 실제 재발한 결함과 핵심 불변조건을 우선한다.

### 12.4 AI 행동 테스트

동일한 원시 요청, 프로젝트와 성공 기준에서 최소한 다음을 비교한다.

- 잘 작성된 산문 기준안
- 부분 컴파일된 작업 패킷
- 필요하면 스킬이 없는 기준안

관찰 항목:

- 최종 성공 기준 충족
- 잘못된 단계 진입과 누락
- 읽은 파일과 context 양
- tool 왕복과 사용자 왕복
- 중단 뒤 복구
- 오래된 evidence 사용
- 결과 수정에 필요한 소유자 수
- `unknown` 또는 미검증을 정직하게 남겼는가

한두 번의 성공은 가능성 증거이며 보증이 아니다. 다만 반복 수를 무한히 늘리지 않고, 다음 제품 결정을 바꿀 만큼만 실행한다.

### 12.5 테스트의 입장과 퇴출

각 테스트는 다음 중 하나를 이름 붙여야 한다.

- 관찰된 실패
- 고정 목적을 지키는 핵심 불변조건
- 외부 호환 또는 안전 제약

어느 것도 지키지 않거나 결과가 어떤 값이어도 제품 결정이 바뀌지 않는 테스트는 추가하지 않는다. 대상 기계가 사라지면 그 기계를 검사하던 테스트도 같은 변경에서 제거한다.

테스트 실패를 없애기 위해 제품 의미를 검사에 맞추지 않는다. 먼저 제품, fixture, harness, 환경과 잘못된 성공 기준 중 무엇이 실패했는지 판정한다.

### 12.6 비례적 실행

- pure function 수정은 해당 단위와 직접 통합 경로를 검사한다.
- renderer 수정은 관련 schema와 생성 결과를 검사한다.
- 판단 산문 수정은 짧은 fresh 해석·행동 시험을 우선한다.
- 실행 흐름이나 고정 목적이 바뀔 때만 종단 비교를 연다.
- release라는 이유만으로 모든 과거 실험을 반복하지 않는다. 현재 release 주장을 지지하는 대표 경로를 실행한다.

## 13. 첫 완전한 소비자 검증: Devflow

이 절은 제품 architecture 설명이 아니라, 앞에서 정의한 범용 시스템이 실제로 충분한지 반증하기 위한 검증 계획이다. Devflow는 새 시스템 안에 내장되는 workflow가 아니라 새 시스템으로 다시 저작할 첫 고난도 소비자다. 아래 표도 기존 Devflow 구조의 유지 또는 변환 계획이 아니라, 개발 workflow의 각 책임이 범용 경계로 분배 가능한지 보는 최초 대조다.

| 영역 | AI가 맡는 판단 | 기계가 맡는 처리 |
| --- | --- | --- |
| 공통 원칙 | 사실과 추정의 의미, 충돌 우선순위 | 용어, 문서 owner, 상태 vocabulary, 관련 모듈 선택 |
| 제품 정의 | 실제 문제, 원하는 변화, 성공 기준의 의미 | 필수 입력, 누락·중복 검사, brief 렌더링, 승인 revision |
| 작업 계획 | 적절한 분해와 의미 dependency | 카드 ID, DAG, 순환, 개수, plan 렌더링 |
| 구현 | 코드 작성과 뜻밖의 변경 판단 | 실행 가능한 작업 선택, 관련 context 구성, 범위·currentness 검사 |
| 검증 | 어떤 실행이 무엇을 증명하는지, 결과의 의미 | 명령 실행, output 수집, 기준별 evidence 연결, report 렌더링 |
| 재개 | 모순하거나 불완전한 상태의 의미 | artifact·revision·approval·evidence에서 다음 단계 계산 |

이 기준 사례에서 Product 같은 의미 중심 단계는 자연어 비중이 높고, Resume·문서 생성·dependency·검증 결과 수집은 기계화 비중이 높을 것으로 예상한다. 모든 단계에 동일한 구조와 비용을 부과하지 않는다.

### 13.1 간단한 pilot과 실제 Devflow의 역할

간단한 natural-language pilot은 새 시스템의 최종 범위가 아니다. 복잡성을 잠시 제거해 부분 컴파일, 판단 함수, renderer, 최소 상태와 `next()` 흐름이 실제로 AI에게 유용한지를 가장 싸게 확인하는 최초 수직 실험이다.

실제 Devflow 수준의 개발 workflow는 첫 번째 완전한 목표이자 stress envelope다. 여기서 stress envelope는 현재 Devflow의 구조를 호환한다는 뜻이 아니라, 그 프로젝트가 드러낸 실제 문제 범위를 새 시스템이 core를 비대하게 바꾸지 않고 수용할 수 있어야 한다는 뜻이다.

```text
간단한 pilot
  → 핵심 상호작용과 비용 가설 판별
  → 작은 core 확정
  → 실제 Devflow 복잡성에 단계적으로 적용
  → core primitive의 조합으로 충분한지 반증
  → 다른 종류의 스킬에서 범용성 확인
```

pilot에서 성공했다는 이유로 Devflow 수용성을 주장하지 않는다. 반대로 Devflow의 모든 예외를 pilot 단계에서 미리 core에 넣지도 않는다.

### 13.2 실제 Devflow가 요구하는 복잡성 범위

새 시스템은 장기적으로 적어도 다음 실제 문제를 표현하고 운영할 수 있어야 한다.

| 실제 문제 범위 | 새 시스템에서 기대하는 해결 축 |
| --- | --- |
| 모호한 요청을 제품 문제와 성공 조건으로 정의 | 목적 산문, 판단 함수, 구조화된 brief renderer |
| 새 프로젝트의 기술·UI 방향 결정 | 조건부 판단 모듈, 결정 artifact, 관련 context 선택 |
| 기존 프로젝트의 문서·코드·결정을 역산 | 기계적 inventory, 반복 work queue, provenance, 부분별 AI 판단 |
| 여러 기능과 작업의 분해·dependency | graph 함수, ID, currentness, work-unit packet |
| 승인 전후의 계획과 구현 경계 | 명시 결정과 대상 revision, 필요한 경우 통제된 write API |
| 구현 중 새 사실과 범위 변경 | 현재 task state, 새 판단 요청, 기존 결과 invalidation |
| 실제 실행을 통한 검증과 회귀 확인 | command 수집, 기준별 evidence 연결, 의미 판정 함수 |
| 세션 중단과 context compaction 뒤 재개 | artifact 재계산, 최소 durable 좌표, 작은 resume packet |
| 여러 AI와 여러 터미널의 병렬 작업 | task 분리, revision compare-and-swap, artifact 충돌 반환 |
| 긴 프로젝트 지식과 결정의 선택적 사용 | 관련도 계산, 조건부 resource, 출처가 있는 요약·검색 |
| 상위 결정 변경의 하위 파급 | artifact dependency와 basis를 통한 stale 판정·재계산 |
| 완료되지 않았거나 관찰할 수 없는 상태 | 명시적 unknown, open decision과 다음 관찰 |

이 목록은 기존 Devflow의 단계와 상태 기계를 복제하기 위한 기능 목록이 아니다. 새 core가 목적·관찰·판단·계산·쓰기·상태·효과·증거라는 책임을 조합해 실제 개발 workflow의 압력을 견딜 수 있는지 확인하는 수용 범위다.

### 13.3 Devflow 수용성의 판정

다음이면 실제 Devflow 복잡성을 잘 내포한다고 볼 수 있다.

- 복잡한 흐름을 추가할 때 AI가 항상 읽는 entry와 목적 kernel이 계속 작다.
- 새 단계는 기존 core 문법 확장보다 domain 판단 함수, artifact와 기계 함수의 조합으로 표현된다.
- 하나의 작업에서 관련 없는 planning·recovery·verification 산문이 전달되지 않는다.
- Brownfield, multi-agent와 resume가 같은 전역 상태를 공유하지 않고 독립 task와 artifact 관계로 결합된다.
- 상위 결정이 바뀌면 하위 결과의 currentness가 기계적으로 무효화되지만, 무엇을 다시 결정할지는 작은 판단 패킷으로 돌아온다.
- 전체 개발 흐름을 완료한 fresh AI가 내부 체계를 설명하지 못해도 사용자의 제품 결과에 도달할 수 있다.
- Devflow를 수용하기 위해 추가한 공통 요소가 다른 스킬에서도 실제로 재사용되지 않으면 core가 아니라 Devflow domain으로 남는다.

### 13.4 범용성 검증의 순서

범용성은 Devflow 기능을 추상적인 이름으로 바꾸는 것으로 증명하지 않는다.

1. 간단한 개발 pilot에서 최소 core의 실용성을 확인한다.
2. 실제 Devflow의 서로 다른 압력—판단 중심, 상태 중심, brownfield, 검증, 병렬 작업—에 적용한다.
3. 같은 primitive를 개발 이외의 판단 중심 스킬과 형식 중심 스킬에 각각 적용한다.
4. 두 외부 사례가 불필요한 Devflow 개념을 요구받지 않는지 확인한다.
5. 공통으로 반복된 기능만 core에 남기고 나머지는 domain package에 둔다.

## 14. 범용성의 경계

핵심 primitive는 특정 개발 workflow에 종속되지 않는다.

- typed fact와 그 출처
- artifact와 currentness
- pure function과 결정적 rule
- 조건부 판단 함수
- 반복 가능한 work queue
- schema와 renderer
- 최소 durable task state
- 현재 작업 패킷

고객 지원 검토, 문서 작성, 조사, 데이터 정리와 운영 절차도 같은 primitive를 사용할 수 있다. 그러나 각 도메인의 판단 기준과 결과 품질은 해당 스킬이 소유한다.

범용성은 모든 도메인 행동을 하나의 거대한 문법에 넣는 것이 아니다. **작은 공통 실행 모델과 도메인별 판단·함수를 결합할 수 있는 것**이다.

### 14.1 완성도는 예외의 수가 아니라 책임 경계의 완결성이다

이 기획이 발생 가능한 모든 미래 문제를 미리 열거하려 해서는 안 된다. 높은 완성도는 새 문제가 생겼을 때 다음 책임 중 어디에서 다뤄야 하는지 찾을 수 있고, 다른 책임을 함께 팽창시키지 않고 고칠 수 있다는 뜻이다.

```text
목적       무엇을 위해 존재하며 무엇을 성공으로 보는가
관찰       기계가 현재 사실로 직접 알 수 있는 것은 무엇인가
판단       AI나 사람이 의미를 해석하거나 선택해야 하는 것은 무엇인가
계산       알려진 입력에서 동일하게 계산할 것은 무엇인가
쓰기       의미 내용을 어떤 정확한 결과물로 만들 것인가
상태       다음 호출과 동시 작업에 필요한 최소 좌표는 무엇인가
효과       실제 세계에서 무엇을 실행하며 누가 통제하는가
증거       무엇이 실제로 일어났음을 어느 권한으로 알 수 있는가
```

새 실패는 먼저 이 여덟 책임의 입력·출력·소유자 사이에서 누락이나 충돌을 찾는다. 기존 책임으로 설명하고 고칠 수 없다면 그때만 새 primitive를 검토한다. 이 방식으로 사례는 확장할 수 있지만 core 개념은 작게 유지한다.

## 15. 비대화와 경직을 막는 설계 규율

다음 신호가 둘 이상 보이면 기능 추가를 멈추고 상위 가설을 다시 본다.

- 같은 실패를 막는 rule이 여러 표면에 생긴다.
- AI가 제출해야 할 내부 상태값이 늘어난다.
- 오류 복구 설명이 정상 사용 설명보다 길어진다.
- 새 기계의 매뉴얼이 제거한 산문보다 커진다.
- 기계 테스트는 늘지만 fresh-agent 행동이나 실제 효과 관찰이 없다.
- 한 모델의 한 번의 실수를 범용 규칙으로 만들고 있다.
- workflow 내부 vocabulary가 사용자 목적보다 더 자주 등장한다.
- 하나의 작업 패킷이 여러 판단과 후처리를 동시에 요구한다.
- artifact에서 계산 가능한 사실을 별도 상태에 복제한다.
- 현재 기능을 제거하면 무엇이 실제로 깨지는지 설명할 수 없다.

그때는 예외를 더 추가하지 않고 다음 순서로 돌아간다.

1. 사용자가 원한 첫 결과를 다시 쓴다.
2. 현재 실패가 의미·전달·행동·효과 중 어디에 있는지 분류한다.
3. 자연어, 기계 함수, 판단 함수, renderer, host 권한 중 실제 소유자를 찾는다.
4. 가장 단순한 대안과 현재 대안을 비교한다.
5. 기존 요소 중 무엇을 제거할지 포함하지 못하는 새 장치는 보류한다.

## 16. 경쟁 가설과 반증 조건

### H1. 잘 구조화한 산문과 파일 트리만으로 충분하다

설명하는 사실:

- 판단 중심의 작은 스킬은 산문만으로도 잘 작동할 수 있다.
- 사람이 간헐적으로 구조를 정리하면 비용이 낮을 수 있다.

반증 관찰:

- dependency, currentness, exact format, 반복 처리에서 같은 오류가 반복된다.
- 산문 기준안이 부분 컴파일 방식보다 더 많은 context와 수정 왕복을 일관되게 사용한다.

### H2. 부분 컴파일된 혼합 구조가 가장 실용적이다

설명하는 사실:

- 절차와 형식은 코드로 줄이고 의미 판단은 유지할 수 있다.
- 현재 작업 패킷으로 context를 제한할 수 있다.

반증 관찰:

- packet 생성과 도구 왕복 비용이 제거한 산문 비용보다 크다.
- AI가 작은 packet만 받고 목적과 중요한 경계를 반복해서 놓친다.
- 구조화 입력을 만들기 위해 결국 원래 산문 대부분을 다시 읽어야 한다.

### H3. 더 강한 host 통합과 실행 통제가 필요하다

설명하는 사실:

- 높은 위험의 실제 effect는 자발적인 도구 호출만으로 강제할 수 없다.

반증 또는 적용하지 않는 경계:

- 대부분의 대상 스킬이 읽기·작성 보조이고 잘못된 effect의 위험이 낮다.
- host 통합 비용이 실제로 방지하는 위해보다 크다.

현재의 잠정 선택은 H2다. H1은 반드시 기준안으로 유지하고, H3는 실제로 강제해야 하는 고위험 효과에서만 연다.

## 17. 기존 구현과 재구현의 관계

후속 개발은 기존 구현을 점진적으로 고치는 방식이 아니다. 기존 Skill Rails와 Devflow의 구현을 명시적인 백업 영역에 격리하고, 새 저장·실행 구조를 빈 기준선에서 세운 뒤 기능을 하나씩 새로 구현하는 방식을 전제로 한다. 다만 두 프로젝트가 드러낸 실제 사용자 필요, 복잡성 범위와 실패 장면은 새 시스템이 해결해야 할 문제 자료로 보존한다.

이 전환은 과거 자료를 삭제한다는 뜻이 아니다. 과거 구현이 새 설계의 형태, 기능 목록, 용어, 호환 요구와 테스트 기준을 선점하지 못하게 하면서도 이미 확인한 실패 장면과 반례를 정확히 대조할 수 있게 보존하는 것이다. 과거 코드가 동작한다는 사실은 새 core에 들어올 이유가 아니며, 과거 계획의 완성도를 높이는 방향으로 새 시스템을 설계하지 않는다.

### 17.1 백업 영역의 성격

- 기존 구현은 실행 정본이 아니라 읽기 전용 참고 자료다.
- 백업으로 옮기기 전에 파일 목록, 현재 revision과 보존 이유를 확인한다.
- 새 build, test, package discovery와 배포가 백업 영역을 현재 구현으로 오인하지 않도록 경계를 분명히 한다.
- 백업 안의 문서·코드·fixture·기능 목록은 존재한다는 이유만으로 새 설계의 요구사항, 테스트 정답지나 호환 의무가 되지 않는다.
- 새 구현은 백업 구현을 import, 호출, 상속하거나 fallback으로 사용하지 않는다.
- 기존 Skill Rails와 Devflow의 package 형식과 public behavior에 대한 호환은 기본적으로 제공하지 않는다. 실제 사용자가 요구하는 독립된 외부 계약이 나중에 확인될 때만 별도 결정으로 연다.
- 백업의 정확한 경로, Git 보존 방식과 이동 순서는 별도 재구현 계획에서 결정한다.

### 17.2 기능별 재구현 순서

각 기능은 다음 순서로 다시 판단한다.

```text
사용자에게 필요한 실제 결과 정의
  → 가장 단순한 산문 기준안 확인
  → 기계화할 반복 비용 또는 실패 경계 확인
  → 새 개념으로 최소 수직 흐름 설계·구현
  → 새 흐름의 행동과 효과를 먼저 관찰
  → 필요할 때만 백업에서 놓친 실패·반례가 있는지 대조
```

과거 코드를 먼저 읽고 새 구조에 맞추지 않는다. 먼저 새 기능의 입력, 출력, AI 판단, 기계 계산과 성공 증거를 독립적으로 정하고 새 코드로 구현한다. 백업 대조는 새 설계를 만드는 입력이 아니라, 새 수직 흐름이 이미 겪었던 실패를 반복하는지 확인하는 후행 반증이다.

### 17.3 과거 지식의 후행 반증 조건

기존 계획과 구현은 새 정본에 재채택하지 않는다. 백업에서 얻은 관찰이 새 설계의 변경 근거가 되려면 다음 조건을 만족해야 한다.

1. 과거의 구조가 아니라 구체적인 실패 장면이나 외부 요구로 표현할 수 있다.
2. 같은 실패 경로가 새 설계에도 실제로 존재한다.
3. 새 설계의 목적과 현재 사용 흐름에서 위해가 발생한다.
4. 가장 단순한 새 해결 위치와 반증 방법을 말할 수 있다.
5. 변경이 기존의 어떤 새 요소를 대체하거나 단순화하는지 말할 수 있다.

조건을 충족하면 과거 코드를 복사하는 대신 관찰된 요구와 반례를 새 용어로 다시 정의하고 새 소유자에서 구현한다. 조건을 충족하지 못한 내용은 백업에 남긴다. “과거에 있었음”, “테스트가 있음”, “나중에 필요할 수 있음”은 새 core에 들어올 근거가 아니다.

### 17.4 재구현의 단위

재구현은 내부 문법이나 하위 라이브러리를 먼저 완성하는 방식으로 진행하지 않는다. 사용자가 실제로 경험할 수 있는 가장 작은 수직 흐름을 하나씩 완성한다.

한 수직 흐름은 가능하면 다음을 함께 가진다.

- 실제 사용자 요청
- AI가 읽는 작은 entry와 현재 작업 패킷
- 필요한 판단 함수 하나
- 필요한 기계 함수와 renderer
- 생성되는 실제 결과물
- 가장 싼 행동·효과 확인
- 아직 구현하지 않은 경계

이 흐름에서 필요성이 관찰되지 않은 범용 문법, 상태 기능, 검사와 adapter를 미리 완성하지 않는다. 두 번째 실제 흐름에서 같은 기능이 다시 필요할 때 공통 primitive로 추출한다.

### 17.5 전환 중의 두 정본 방지

- 새 구현과 백업 구현을 동시에 현재 정본으로 운영하지 않는다.
- 새 구현이 아직 준비되지 않은 기능은 미지원이다. 백업 구현으로 보충해 현재 기능처럼 제공하지 않는다.
- 새 시스템의 entry, 실행 경로, 테스트와 문서는 처음부터 새 소유자만 가리킨다.
- 백업 구현을 호출하는 임시 우회, compatibility shim과 fallback을 만들지 않는다.

## 18. 최초 판별 계획

상세 구현을 정하기 전에 작은 대표 workflow에서 다음 세 버전을 비교한다.

1. 짧고 잘 구조화한 산문 버전
2. 산문 + 부분 컴파일 + renderer + 최소 상태 버전
3. 필요하면 효과가 도구 API를 통과하는 통합 버전

대표 장면:

- 정상적인 작은 작업
- 세션 중단 뒤 재개
- 오래된 검증이나 변경된 원본
- 두 터미널이 같은 artifact를 갱신하려는 충돌
- exact format 문서 생성
- 의미 판단이 불충분해 사람에게 되돌려야 하는 장면

결과별 행동:

- 산문과 혼합 구조의 행동 품질이 같고 산문이 더 싸면 산문을 선택한다.
- 혼합 구조가 상태·형식·누락 오류를 줄이고 총비용도 낮추면 해당 기계만 채택한다.
- host 통합만 실제 고위험 effect를 막는다면 그 효과 범위에만 통합한다.
- 결과가 혼합되면 스킬 전체의 등급을 만들지 않고 기능별로 소유 방식을 나눈다.
- 관찰이 부족하면 구현을 확대하지 않고 미결정과 다음 관찰을 남긴다.

## 19. 이 최초 기획의 성공 조건

이 문서는 다음을 가능하게 하면 역할을 다한다.

- 후속 기획자가 과거 구현을 답안으로 삼지 않고 최초 목적에서 설계를 시작할 수 있다.
- 무엇을 자연어, 기계 함수, 판단 함수, renderer와 host가 맡는지 설명할 수 있다.
- 상태, 쓰기, 테스트가 항상 필요한 기능이 아니라 조건부 수단임을 이해할 수 있다.
- 새 기능을 추가할 때 무엇을 제거하거나 단순화하는지 요구할 수 있다.
- 상세 개발 계획에서 먼저 비교해야 할 기준안과 반증 조건을 찾을 수 있다.
- Devflow뿐 아니라 낯선 스킬에서도 같은 경계를 적용하되 도메인 판단을 범용 문법으로 흡수하지 않는다.

## 20. 이 문서가 결정하지 않는 것

- 구현 언어와 배포 형식
- 구체 schema 또는 DSL 문법
- 상태 저장 위치와 파일 형식
- host adapter의 수와 우선순위
- 실제 API 이름
- release 단계와 migration 계획
- 기존 구현을 보존할 백업 디렉터리의 실제 경로와 이동 순서
- 최종 테스트 횟수와 합격 수치

이 선택들은 최초 원점 기획을 여러 독립 검증으로 반증한 뒤 별도의 상세 기획 문서에서 결정한다.

## 21. 후속 상세 기획이 답해야 할 질문

1. 대표 스킬의 산문 중 실제로 몇 줄과 몇 byte가 기계 계산으로 제거되는가?
2. 한 invocation의 고정 context와 조건부 context는 기준안보다 얼마나 작은가?
3. `next()`가 자동 관찰할 사실과 AI에게 물어볼 판단은 정확히 무엇인가?
4. 판단 함수가 목적을 잃지 않도록 항상 포함할 최소 kernel은 무엇인가?
5. structured content가 자유로운 의미를 지나치게 축소하지 않는가?
6. renderer가 기존 사용자 편집을 어떻게 보존하는가?
7. 여러 터미널의 task identity와 revision conflict를 가장 단순하게 어떻게 처리하는가?
8. artifact에서 계산 가능한 상태와 저장해야 하는 상태의 경계는 무엇인가?
9. 일반 스킬 모드와 host 통합 모드가 각각 어디까지 보장한다고 말할 수 있는가?
10. 어떤 기계 테스트가 실제 위험을 막으며 어떤 검사는 단지 구조 점수표인가?
11. fresh-agent 기준안 비교에서 품질, 비용과 복구성을 무엇으로 측정하는가?
12. 기능 하나를 추가할 때 기존 무엇을 제거할 것인가?
13. 기존 구현을 새 실행·build·test 경로에서 완전히 격리하면서 어떤 실패 자료만 후행 반증에 사용할 것인가?
14. 첫 번째 최소 수직 흐름은 어떤 실제 요청으로 끝까지 관찰할 것인가?

## 22. 범용 탐구 체계의 적용

이 기획은 [범용 AI 스킬 개발을 위한 탐구·절제·환류 체계](../guide/universal-ai-skill-inquiry-framework.md)를 다음 방식으로 사용했다.

- **고정 목적과 잠정 수단을 분리했다.** 최초 문제는 보존하되 부분 컴파일, 상태와 API는 반증 가능한 수단으로 두었다.
- **과거 실패를 규칙으로 복제하지 않았다.** 실패에서 “기계화 금지”가 아니라 기계의 책임을 넓힐 때 생긴 인과만 추출했다.
- **경쟁 가설을 유지했다.** 산문만으로 충분한 경우, 혼합 구조가 유리한 경우, host 통합이 필요한 경우를 같은 출발선에 두었다.
- **의미·전달·행동·효과를 분리했다.** schema와 테스트가 통과해도 AI 행동이나 사용자 효과가 성공했다고 말하지 않는다.
- **새 장치의 입장권을 정의했다.** 현재 실패를 제거하고 총복잡성을 낮추지 못하는 상태·검사·문법은 추가하지 않는다.
- **증식 신호와 복귀 절차를 포함했다.** 구현 중 구조가 다시 비대해질 때 최초 목적과 가장 단순한 대안으로 돌아갈 수 있게 했다.
- **검증의 비례성을 반영했다.** 테스트 개수보다 다음 결정을 바꾸는 대표 관찰을 우선한다.
- **책임 소유와 AI 작업 비용을 명시했다.** 목적·관찰·판단·계산·작성·상태·효과·증거가 어디에 속하는지 먼저 가르고, 새 장치가 줄이는 context·왕복·복구 비용을 함께 본다.
- **greenfield 재구성과 과거 자료의 경계를 명시했다.** 검증된 요구와 실패 장면은 보존하지만 과거 구조·호환·test 기대값은 새 기준선으로 자동 승계하지 않는다.

이 체계는 제품에 그대로 탑재할 workflow가 아니다. 이번 기획이 목적을 잃거나 과거 실패를 새 문법으로 복제하지 않도록 판단을 구성하는 데 사용한 방법이다.

### 22.1 현재 평가

이 프레임워크의 핵심 개념은 앞으로 스킬을 기획하고 큰 변경을 검토하는 기준으로 사용하기에 충분히 유효하다.

특히 다음은 직접적인 이점이 있다.

- 목적과 구현 수단의 권위를 분리해 이미 투자한 구조를 답안으로 삼는 오류를 줄인다.
- 사실, 해석, 가설과 미검증을 구분해 한 번의 AI 판단이 곧 제품 규칙이 되는 것을 막는다.
- 국소·상위 계약·비문제 가능성을 함께 비교해 같은 위치에 예외를 계속 추가하는 일을 줄인다.
- 의미·전달·행동·효과를 나누어 test green을 실제 유용성과 혼동하지 않게 한다.
- 새 규칙·검사·역할·기계가 제거할 기존 비용과 운용 비용을 먼저 묻게 한다.
- 반복 실패에서 구현뿐 아니라 목표·성공 기준과 전제를 다시 보는 복귀 경로를 제공한다.

그러나 현재 문서가 효과적이라는 행동 증거는 아직 없다. 철학적·논리적 구성이 타당하다는 판단과, 실제 스킬 개발에서 재작업·과잉 구현·컨텍스트·사용자 교정 비용을 줄였다는 증거는 다르다.

### 22.2 그대로 상시 실행 규약으로 쓰지 않을 이유

프레임워크는 넓은 문제를 다루기 때문에 문서 자체가 길다. 모든 작업에서 전체를 읽고 모든 카드와 검증을 수행하면, 이 문서가 막으려는 절차 증식과 컨텍스트 부담을 다시 만들 수 있다.

이번 검토에서 원문에 작업 종류별 진입 경로와 네 줄짜리 공통 핵심이 추가되었다. 또한 책임 소유, AI 작업면과 context 경제성, 다중 세션 상태, renderer 기반 작성, 테스트의 입장·폐기 조건과 greenfield 격리 원칙이 명시되었다. 따라서 기획과 구현의 주요 실패 유형을 다루는 논리적 범위는 이전보다 충분해졌다.

아직 보완이 아니라 **실측으로 판정해야 하는 지점**은 다음과 같다.

- 여러 절에 반복되는 목적·가설·비례성·증식 방지 개념을 선택형 진입에서 실제로 한 번만 읽게 되는가?
- 원문 안의 네 줄 공통 핵심만으로 충분한가, 별도의 결정적 projection이 context를 더 줄이는가?
- 가장 작은 작업 맥락과 탐구 카드의 필수 필드를 더 줄여도 판단 품질이 유지되는가?
- framework를 사용한 경우와 사용하지 않은 경우에 결과·재작업·비용 차이가 있는가?
- 소유자와 AI가 framework를 잘 요약한 것이 아니라 실제로 불필요한 추가물과 잘못된 결정을 줄였는가?

### 22.3 권장 운용

원문은 철학과 전체 복귀 경계를 소유하는 maintainer reference로 유지한다. 우선 원문의 0.1 진입 경로로 현재 위험에 필요한 절만 선택한다.

```text
짧은 진입 라우터
  → 국소 작업: 고정 목적 + 반례 + 최소 확인
  → 불확실한 선택: 경쟁 가설 + 가장 싼 판별
  → 기반·반복 실패: 실패 재구성 + 파급 + 독립 반증
```

실측에서 원문 내 진입 경로만으로도 불필요한 context가 남는다면, 후속 상세 기획에서 다음을 별도 산출물로 검토한다.

- 한 화면 안에 들어오는 진입 라우터
- 국소 작업용 최소 카드
- 불확실한 선택용 탐구 카드
- 반복 실패·기반 변경용 전체 reference route
- 완료 보고용 의미·전달·행동·효과 구분

이 projection은 미리 필요하다고 확정한 기능이 아니다. 비용 차이가 관찰될 때만 만든다. 만들 경우에도 원문을 다시 정의하는 두 번째 정본이 아니라, 원문의 선택 규칙에서 결정적으로 생성되거나 원문 절로 연결돼야 한다.

### 22.4 프레임워크 자체의 판별

앞으로 이 프레임워크를 프로젝트의 기본 기획 기준으로 채택하되, 효과는 다음 비교로 확인한다.

- framework 없음
- 짧은 선택형 projection만 제공
- 현재 전체 framework 제공

같은 설계 문제를 깨끗한 AI 문맥에서 수행하고 다음을 비교한다.

- 최초 목적에서 벗어난 결정 수
- 필요 없이 추가한 규칙·문서·검사 수
- 사용자에게 다시 교정받은 핵심 전제 수
- 결정까지 읽은 context와 소요 왕복
- 반례 발견 후 올바른 소유자로 돌아간 비율
- 결과가 실제 구현 계획에 사용 가능한 정도

짧은 projection이 같은 품질을 더 적은 비용으로 만들면 원문은 배경 reference로 남기고 projection을 기본 진입으로 사용한다. 전체 framework가 기반 기획에서만 추가 가치를 보이면 그 조건에서만 연다. 어느 경우에도 문서 준수율이나 작성한 카드 수를 성공 점수로 사용하지 않는다.

## 23. 동결 선언 자리

이 최초 방향성 기획은 사용자의 확인으로 동결되었다. 이후 이 문서는 수정·재작성·축약·확장·이동·대체하지 않는다.

```text
동결 상태: 최초 방향성 기획 완료
동결 일자: 2026-09-13 KST
후속 문서: 별도로 작성할 상세 개발 기획 문서
```

동결 후 새로운 증거가 이 문서의 수단 가설을 반증하더라도 원문을 고치지 않는다. 후속 문서가 반증된 전제, 새 관찰, 채택한 대안과 이 최초 기획에서 계속 보존하는 목적을 기록한다.

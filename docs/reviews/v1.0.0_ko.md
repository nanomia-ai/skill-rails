# Skill Rails v1.0.0 리뷰

문서 상태: 완료 버전의 판단 기록  
검토일: 2026-09-15 KST  
대상 버전: root package와 authoring package `1.0.0`

## 결론

Skill Rails v1.0.0은 **실제 스킬 저작과 제한된 Devflow 이전을 시작할 수 있는 첫 안정 버전**으로 채택한다. 알려진 재설계 blocker나 방치된 출력 결함은 없다. 다만 이 판정은 모든 스킬·host·model에서의 반복 성공, 일반 산문 대비 인과적 비용 우위 또는 Devflow 전체 성공을 증명하지 않는다.

`1.0.0`은 과거 v0.x 구조의 호환 완성이 아니다. 실패한 P0/P1/P2, V5 runtime, trace store와 Devflow 기계화를 계승하지 않고, 다음 새 계약이 처음 함께 닫힌 버전이라는 뜻이다.

- 짧은 canonical source graph에서 standalone skill을 deterministic하게 만든다.
- 의미 판단과 host 행동은 AI·사용자에게 남긴다.
- 반복 가능한 build, provenance, currentness와 한 출력의 안전 기록만 필요한 만큼 기계화한다.
- 구조·행동·effect·비용 증거를 서로 대신 사용하지 않는다.

## 확신의 근거

강한 확신을 가질 수 있는 범위는 다음과 같다.

1. 같은 source의 두 build는 byte-identical tree를 만들고, generated artifact 무결성과 source currentness를 별도로 검사한다.
2. generated target은 source repository, sibling skill, global Skill Rails runtime과 legacy capsule 없이 동작하며, 설치된 target의 `check`가 receipt에 결합된 package·core version을 함께 반환한다.
3. 정상 `npx skills@latest` repository 경로로 Codex와 Claude Code 양측에 설치했다.
4. 별도 `rollout-lens` 프로젝트에서 Plan·Work·Verify 세 target과 Work·Verify의 공통 규약 owner 하나를 저작했다.
5. fresh Codex Sol medium과 Claude Opus medium이 설치된 target을 발견해 실제 effect를 만들었고, coordinator와 후계 maintainer가 결과 bytes와 테스트를 다시 확인했다.
6. default product 검증은 31/31, 실사용 소비자 프로젝트는 47/47을 통과했다.

정확한 구현·host·effect 증거는 `../implementation-verification_ko.md`와 `../../evals/m8/results/post-release-real-use-vertical-slice-2026-09-14.json`이 소유한다. 이 리뷰는 그 증거를 복제하거나 확장하지 않는다.

## 저작 모델

`authoring`은 문서 작성만을 뜻하지 않는다. 사람이거나 저작 AI가 편집하는 **canonical skill source package**를 뜻한다. 여기에는 skill entry, target descriptor, 공유 의미 module과 필요한 기계 계약이 들어간다.

```text
authoring-package.json
  └─ authoring/skill-rails/        사람이 수정하는 정본
       └─ target descriptor
              │
              ▼ deterministic build
       skills/skill-rails/         설치기가 전달하는 generated 결과
```

루트 `authoring-package.json`은 Node package나 별도 실행 프로젝트가 아니다. Skill Rails builder가 source graph의 package id, version, module과 target 위치를 읽는 manifest다. `package.json`은 core CLI와 test의 Node package 계약이고, 두 파일은 이름이 비슷해도 역할이 다르다.

Generated `skills/skill-rails/`는 직접 수정하지 않는다. `authoring/`과 manifest의 owner를 바꾼 뒤 rebuild하며, receipt가 source와 generated bytes의 관계를 증명한다.

설치된 스킬의 `scripts/run.mjs check`는 별도 버전 파일이나 module별 버전을 만들지 않고 그 receipt에서 `packageId`, `packageVersion`, `coreVersion`, `targetId`와 tree hash를 함께 반환한다. `packageVersion`은 저작한 skill package의 버전이고 `coreVersion`은 그 artifact를 만든 Skill Rails builder 계약의 버전이다. Git tag는 공개 repository release 좌표이며, 설치된 bytes의 자기 식별은 receipt가 소유한다.

## 남아 있는 한계

다음은 알려진 결함이 아니라 아직 관찰 범위를 넓히지 않은 항목이다.

- Devflow 전체를 새 구조로 이전한 결과
- 여러 프로젝트·host version·model에서의 장기 반복성
- 일반 산문 기준안 대비 정확한 token·시간 절감률
- 두 개 이상의 declared output을 한 transaction으로 관리하는 요구
- 실제 lost update와 복잡한 concurrent writer 장면
- POSIX에서 legacy capsule mode가 동일하게 복원되는지

이 항목을 닫기 위해 synthetic matrix, validator, runtime mode 또는 상태 기계를 미리 추가하지 않는다. 실제 사용에서 현재 결정을 바꿀 장면이 발생할 때만 가장 작은 관찰을 연다.

## 사용 합격선과 재개 조건

현재 합격선은 **Skill Rails로 실제 Devflow의 첫 단위를 prose-first·한 owner·현재 artifact 우선으로 저작해도 됨**이다. 첫 적용 결과는 그 target과 장면에만 귀속한다.

다음 중 하나가 실제로 나타나면 core를 수정하기 전에 제품 경계를 다시 검토한다.

- 첫 두 target에서 큰 always-read shared module이 생긴다.
- 한 declared output으로 소유할 수 없는 실제 multi-output 요구가 생긴다.
- fresh AI가 같은 deterministic 판단을 반복해서 틀리고 prose 또는 현재 record-only 경계로 복구되지 않는다.
- 실제 lost update가 재현된다.
- 새 장치의 예상 절감보다 읽기·실행·유지 비용이 더 커진다.

# Starting a new package

- Location: a new package's source lives in `source/` at the project root with `source/skill-package.json` as its manifest; a further package takes its own folder under `source/` with the same shape, so a later session finds every package without asking. An existing package stays where it is.
- Before its first file: if no project instruction keeps its current state for a later session, ask once whether the project will keep the recommended maintenance documents, its own, or none, since a later session recovers the build root, delivery route, and open questions only from what the project records. Only when the user chooses the recommended ones, or later asks for them, set them up with `references/maintenance-docs.md`; then the project's own instructions own them.
- Then tell the user how the work runs from here, in their language, so they can follow it without knowing Skill Rails. The four points and their order are fixed, the words are free: the skill is designed and refined as source in `source/` for as long as they like, and nothing is built meanwhile; when they ask for a build or a test, the source is built into a standalone skill folder, each file placed where its declarations put it and each declared tool shipped with it; the delivery route is chosen with them before the first build, and a test builds, carries that route out on this machine, and has a fresh AI use the result; from then on changes are made in the source, and rebuilt, tested, or delivered when they ask.
- From an existing skill: when the user wants a skill folder they already have brought under source, leave the original where it is, unchanged; it stays in use, and stays what the new build is compared with, until the user retires it. Never put the build in place over the original's folder: for a test, place it where the original is not also loaded, so each run is known to have used one or the other. Before moving any file, show the user the map: for each file, the owner it becomes — `SKILL.md` the entry, its frontmatter kept as written; Markdown the AI reads a reference, or a module when several skills share it; scripts, with the templates and data they use, a tool, with scripts that import one another kept together in one folder tool so their file names and imports still work (`references/tools.md`); a file another program or a person reads at a fixed path an entry in the target's `files` — where its source will live, which delivered paths change (references are delivered flat as `references/<file name>`, tools as `scripts/<id>…`), the mentions in prose and code that must change with them, and anything that fits no owner. When the skill is large — many scripts, several skills sharing files, paths written into code — tell the user the move will take several steps they follow and review with you, one skill or one group of files at a time, and that it is done when the build does everything the original did. Each step is an ordinary source change: its review checks for regressions against the original, and its test gives the original and the build the same task, as `references/build-and-test.md` describes for a change that replaces something.

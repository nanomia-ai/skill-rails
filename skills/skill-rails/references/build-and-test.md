# Build, check, test, and gate

Build into the root the project's own instructions record; otherwise the root follows the delivery route, which `references/delivery.md` owns: a guided route builds with `--out-root <project root>`, which places each target in `skills/<targetId>/`, and a way of the project's own builds into the structure decided with it. The built folder is the whole build. Once the route is chosen, record the build root and the route where the project keeps its current state so the next session reuses them; if the project keeps none, expect to choose again.

Build one target first, review its receipt and generated diff, and verify deterministic delivery and currentness before claiming delivery: build it twice and compare the tree hashes, then run `check` with the source to confirm the folder is intact and source-current, two separate answers. A built folder holds `SKILL.md`, its references, the tools and record runtime it declares, and the receipt; anything else in it is a hand edit the next build refuses. When the user asks for a test, run it on the copy the route put in place on this machine, giving the fresh AI only that skill and the task the user named, or else one or two realistic tasks of its main use; read how it worked as well as what it produced, since needless steps the skill causes show only in the run; an artifact or hash check does not prove that a fresh AI understood or used it. When that test covers a target that ships tools, also run `check` on the installed copy and run from it the tools the test relies on: a route may drop or rewrite files on the way, and some installers skip names such as `metadata.json` or `__pycache__`.

At an adoption or release decision, run the smallest realistic fresh-use observation that could change it and reread the actual effect, within the user's authorized scope; ask only for any scope or permission still missing, and what was not observed stays `unproven`. When the decision is whether the skill or a change beats what it replaces, give the same task to a run without it, or with the previous version, and compare the effects. Scope that observation by the decision's distinct failure risks, not by target count: one observation may cover several targets, and any risk it does not actually exercise stays `unproven`. Record `proven`, `failed`, and `unproven` separately; do not grow a matrix after the decision is already bounded.

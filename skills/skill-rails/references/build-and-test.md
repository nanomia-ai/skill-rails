# Build, check, test, and gate

This file owns, in this order, building and checking a target, its saved test tasks, running a test, measuring and tuning when the skill starts, and the adoption or release gate.

Build into the root the project's own instructions record; otherwise the root follows the delivery route, which `references/delivery.md` owns: a guided route uses the project root as the build root and places each target in `skills/<targetId>/` under it, every target with `--out-root <project root>` or one with `--target <targetId> --out <project root>/skills/<targetId>`, and route D, the project's own way, builds into the structure settled with the user. The built folder is the whole build. Once the route is chosen, record the build root and the route where the project keeps its current state, `docs/current.md` with the recommended maintenance documents or wherever the project's own instructions say, so the next session reuses them; if the project keeps none, say that the next session will have to choose again rather than starting a record of your own.

Build one target first, read its receipt and generated diff, and verify that the build is deterministic and current before reporting it built: build it twice and compare the tree hashes, then run `check` with the source to confirm the folder is intact and source-current, two separate answers. A built folder holds `SKILL.md`, its references, the tools, `files`, and record runtime it declares, and the receipt; anything else in it is a hand edit the next build refuses.

## Test tasks

A target's test tasks are kept with its source, as a code project keeps its tests, so that each test asks the same questions and shows whether a change broke what already worked. They live in `tests/tasks.md` beside the target's descriptor, with the input files the tasks use in the same `tests/` folder; the build reads only what the descriptor declares, so none of it ships, but a route that commits the source commits them too, so say so when an input holds real data. When the user asks for a test, first propose the tasks it needs that are not saved yet — the task the user named, one for behavior added since the last test, or, when the target has none, one or two realistic tasks of its main use — and save them once the user agrees, before any run. Change a saved task only when the requirement it checks has changed or an item fails to check it, never to make a failing run pass.

Each task states what must hold, written before any run, so the run is judged against it rather than read into it afterward. An item names a fact about the result, or about how the work went, that the outputs or the run's record can show, or that the user judges from them where the result is a matter of taste, and it is one a wrong or careless run would fail: the total equals the amount computed from the inputs, not merely that a total was written. When no saved start task covers the current description, or a run showed the skill starting when it should not or staying silent when it should start, give its start tasks of their own: one or two requests that should start it without naming it, written as a user would really write them, with the detail that makes the skill worth consulting, since a host answers a bare request by itself; and one or two near-misses that share its words but need something else. A skill that starts only when named gets only the near-misses, which must not start it. A start task that checks nothing beyond whether the skill starts needs no Inputs or Must hold, since its Start line says what must hold. Each task sits under its own `##` heading, in this shape:

```markdown
## <task name>
Request: <what the user would type>
Start: named | unnamed, should start | unnamed, must not start
Inputs: <files in tests/ given to the run, or none>
Must hold:
- <a fact the outputs or the run's record can show, or the user judges from them>
```

## Running a test

When the user asks for a test, run it on the copy the route put in place on this machine, with a fresh AI that has none of this conversation, working on a copy of each task's inputs so that its outputs never land among the saved ones. For a named task, give a subagent or a new session of the host that skill and the request. For an unnamed task, leave the skill where the host finds it and send the request with its inputs, neither naming the skill nor handing it over, in a new session of each host the skill is delivered to, since starting is that host's own choice; read from the run's record whether it started. Judge each item with the evidence from the outputs or the run's record that decides it; an item nothing shows has not held, and an item that would also hold for a wrong result is a weak test to rewrite with the user, not a pass. Read how it worked as well as what it produced, since needless steps the skill causes, and exact work the AI did by hand that a tool could own, show only in the run; an artifact or hash check does not prove that a fresh AI understood or used it. When that test covers a target that ships tools or files, also run `check` on the installed copy and run from it the tools the test relies on: a route may drop or rewrite files on the way, and some installers skip names such as `metadata.json` or `__pycache__`.

A task that passes as expected runs once. Before acting on a single run whose outcome turns on a judgment rather than a tool — changing the source or the description for a failure, or accepting a result that surprised you, including a failure that appeared when the host or model changed — run that task again, since one run shows that a behavior can happen, not that it holds; say how many runs a result rests on. When what must be repeated is whether an unnamed task starts, repeat it with `start-rate` below.

Record each run where the project keeps its evidence — the build it used (for a `start-rate` measurement, the description and models it measured), each item as `proven`, `failed`, or `unproven` with its evidence, and how many runs — so that a later test knows what held before; a project that keeps none loses it, so say so rather than starting a record of your own.

After a change, run the saved tasks the change could affect along with any new one. The items say what must hold, so each run is judged against them and the previous version need not run again. A failed item is a failure to resolve whatever its cause; one that held before and still fails when run again points to a regression, and the previous version runs only when telling a regression from a failure the skill always had would change the fix.

## Measuring and tuning when it starts

Whether a host starts a skill turns on its `name` and `description`, read beside every other skill the host holds, and varies from run to run, so one run shows little about it. The CLI's `start-rate` measures it from the source, with no build: for each unnamed task in `tests/tasks.md` it starts several fresh sessions of each host named, each in an empty temporary folder holding only the skill's frontmatter, the `files` a host reads, and a body that marks the moment the host opens it, and counts the runs that opened it; a should-start task passes when at least half of its runs started the skill, a must-not-start task when fewer than half did. Name every host the skill is delivered to — `claude`, `codex`, or a host file giving another host's skill folder and a headless command that reads the request on standard input — and run it from a shell that can start those hosts. Each run is a real session billed to the user, so tell the user how many runs a measurement takes, tasks times runs times hosts, and measure once they agree. `claude` and `codex` run the model each host is set to use, the one its users meet; models start skills differently, so to measure another, give a host file with that host's model option, and record which model each measurement used. A copy of the skill installed for the user would be the one the host shows, so the tool hides it on the hosts it knows and reports how; for another host, take that copy out of the host's reach for the measurement. The project's own skills and instructions are not in that folder, so a rival only the project holds stays `unproven`. Built and installed copies keep the description they were built with, so after it changes, a test of the installed skill confirms it when the user asks for one.

Tune the description when the user wants it to start more reliably, such as after a start task failed or before the skill is shared widely; offer it then rather than starting it unasked. A rate over one or two requests cannot tell a better description from a lucky run, so first propose a larger start set, about eight to ten requests of each kind: should-start requests varied in phrasing, length, and detail, including ones that never use the skill's own words and ones where a neighboring skill competes but this one should win; and near-misses that share its words or subject but need something else, never requests that are plainly unrelated, which test nothing. Save them as start tasks once the user agrees. With three or more tasks of a kind, `start-rate` holds out two in five of them, the same ones every time, and reports only how many of those passed. Rewrite the description from the failures among the rest, toward the kind of intent each failure shows rather than a list of the failing requests, since the description is read beside every request and a list fits only the requests you saw; after a rewrite that did not help, change its structure rather than adding words. Measure each rewrite, and stop when every tuning task passes, after five rounds, or at a limit the user set. Keep the description with the most held-out passes summed across hosts, since the held-out tasks are the only ones it was not written against; when those tie they tell the descriptions apart no further, so the one with more tuning passes wins, and the earlier one only when both tie. Put the kept description into the source, review it as any source change, and report each measured description with its scores, the runs they rest on, and what the tool hid on each host, saying so when the held-out passes did not rise and the choice rests on the tuning tasks.

## Adoption and release

When the user is deciding whether to adopt or release the skill, name the smallest realistic test of the installed skill that could change that decision. Run it only once the user asks for it or for the release, then reread the actual effect; ask only for any scope or permission still missing, and what was not observed stays `unproven`. When the decision is whether the skill or a change beats what it replaces, give the same task to a run without it, or with the previous version, and compare the effects. Scope that observation by the decision's distinct failure risks, not by target count: one observation may cover several targets, and any risk it does not actually exercise stays `unproven`. Do not grow a matrix after the decision is already bounded.

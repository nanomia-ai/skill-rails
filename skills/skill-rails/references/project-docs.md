# Project maintenance documents

A project that adopts the shape below owns these documents through its `AGENTS.md` from then on; later changes here do not reach it.

## What a later session must recover from disk alone

What the package is for, how it is composed, where source and builds live and which delivery route was chosen, what is open, and why a non-obvious choice was made. Documents are the current interface to that knowledge, not a log: Git keeps history, and a document that starts recording history has lost its job.

## Setting it up

One router. Add the section below to an existing `AGENTS.md` with the user's consent, never overwrite; a project that already routes documents elsewhere registers these there rather than gaining a rival. A host that reads its own entry file gets one line pointing to `AGENTS.md`; a host that reads `AGENTS.md` itself needs nothing. At setup only the router section and `docs/current.md` exist; write `current.md` from what is known now, and an unknown build root or route is an open question, not a guess.

The section is written so the rules close without this file: every wall and every criterion a later session needs is inside it, and nothing in it points back here. Fixed are the read order, the update column with its walls, and the closing lines; free are the purpose line, the wording of what each document owns, headings, and language, which is the project's own.

```markdown
## Maintenance documents
<one line: what this project's skill package does>
Read `docs/current.md` first; open the others only when the task needs them. One owner per fact; every other document links to it, so two statements can never disagree.

| document | owns | update and its wall |
|---|---|---|
| `docs/current.md` | purpose; what each target, module, and reference is for; source root, build root, delivery route and its frame files; open questions | replace in place, in the same change that alters what it states. Never a line about what changed or when: such a line belongs in `changes/` or Git, and finding one is the signal to move it |
| `docs/decisions/<slug>.md` | one question: current answer, alternatives weighed, what would reopen it | made only when losing the reason would make a next worker repeat the debate or undo the choice; replace when the answer changes; delete when it no longer protects a judgment. A decision that restates a rule instead of its reason sits in the wrong owner |
| `docs/plans/<slug>.md` | work in progress: purpose, scope and out of scope, done condition | made when a later session may have to continue the work; when its done condition is met, move what should outlive it into `current.md`, a decision, or a change record, then delete it. A plan whose work is already reflected there is stale: trust what is reflected |
| `docs/changes/<YYYY-MM-DD>-<slug>.md` | one change: what and why, evidence as `proven`, `failed`, `unproven`, follow-ups, each also opened in `current.md`'s open questions, which a record alone would bury | written when a change carries verification evidence or a follow-up a next worker needs, else the commit message is enough; write once, never edit, a correction is a new record. A change record that states current rules sits in the wrong owner |
| `docs/research/<slug>.md` | sourced findings with the date checked | made when the project relies on a fact from outside it that could change; replace when superseded; delete when nothing relies on it |

Create a folder when its first file is needed; this section is the only index of these documents. The built skill folders are generated by Skill Rails from the source root into the build root that `docs/current.md` records: change the source, never the output: the next build and `check` refuse an edited output, so discard the edit rather than merge it, and for the exact source graph run its `overview` without saving it. Beyond this shape, length, headings, subfolders, and wording are free.
```

# AI 스킬 진화를 위한 탐구·절제·환류 방법

## 0. 이 문서가 해결하려는 실패

이 문서는 AI가 읽고 행동하는 스킬과, 그 스킬을 저작·전달·생성·검증하는 도구를 새로 기획하고 점진적으로 개선할 때 쓰는 판단 방법이다. 특정 저장소·프레임워크·빌드 도구·단계 이름을 전제하지 않는다.

이 체계는 세 실패를 막기 위해 존재한다.

1. 큰 계획을 한 번에 완성하려다 AI가 빈틈을 자기 판단으로 메우고, 의도하지 않은 결정을 만드는 실패.
2. 구현 중 발견한 국소 문제를 같은 위치에서 계속 고치다가, 실제 원인·목적·경계는 놓치는 실패.
3. 불확실성을 없애려 규칙·예외·검사·문서를 늘리고, 그 추가물이 다시 새 문제를 낳는 증식 실패.

목표는 더 많은 규칙이 아니다.

> 소유자가 정한 목적을 보존하면서, 가장 작은 충분한 구조로 실제 AI 행동과 실제 효과를 개선한다.

이 체계는 제품의 실행 규칙이나 모든 작업에 붙이는 장문 프롬프트가 아니다. 스킬의 기획·구현·검증·복구에서 **어떤 질문을 열고, 무엇을 근거로 결정하며, 언제 멈출지** 정하는 상위 탐구 기준이다. 비어 있는 입력을 AI가 추측으로 채우지 않는다. `미결정`으로 남기거나 소유자에게 되돌린다.

### 0.1 이 문서의 지위와 사용하는 방법

이 문서의 전체 본문은 목적, 근거와 복귀 경계를 보존하는 참조 원문이다. 매 작업에서 전부 읽고 모든 양식을 작성하는 것이 준수의 의미는 아니다. 아래의 **공통 핵심**만 먼저 확인하고, 현재 결정을 바꿀 수 있는 절만 연다.

```text
모든 작업의 공통 핵심:
  1. 지켜야 할 목적과 금지
  2. 현재 확인된 사실과 미확인
  3. 지금 걸려 있는 하나의 결정
  4. 결정 권한과 다음 행동을 바꿀 최소 증거
```

| 현재 작업 | 먼저 여는 절 | 조건부로 여는 절 |
|---|---|---|
| 새 스킬·새 기반 기획 | 1~5 | 기술 미지가 있으면 6, 첫 구현을 약속할 때 7~8 |
| 국소적이고 되돌릴 수 있는 구현 | 1, 2, 4.1~4.2, 7 | 전달·행동이 바뀔 때만 8 |
| 기술 후보 비교 | 1, 2, 4.1, 4.5, 6 | 파급 경계를 건너면 4.3, 고위험이면 10 |
| 자연어·행동 계약 저작 | 1, 2, 8.1~8.3 | 정확한 형식·상태가 있으면 7.3~7.5 |
| 반복 실패·비대화 복구 | 1, 2, 5.1, 9 | 목적·전달 계약이 흔들리면 5 전체, 독립 반증이 필요하면 10 |
| 완료·배포 판단 | 4.4, 8 | 고위험 주장 또는 불일치가 있으면 10 |

절 번호는 고정 의식이 아니라 탐색 경로다. 필요한 판정이 끝나면 더 깊은 절을 자동으로 열지 않는다. 별도의 짧은 실행용 요약이나 도구가 생기더라도 이 원문의 의미를 다시 정의하지 않고, 선택된 절과 현재 입력만 투영해야 한다.

## 1. 먼저 제공할 작업 맥락

```text
작업 이름:

고정 목적:
  이번 작업이 끝나도 바꾸면 안 되는 사용자 가치·행동 변화·금지는 무엇인가?

성공 증거:
  무엇을 관찰하면 목적에 가까워졌다고 말할 수 있는가?

현재 사실:
  소스, 문서, 생성물, 도구 실행, 실제 사용에서 이미 확인한 사실은 무엇인가?

과거 실패 자료:
  실패 장면, 이미 시도한 수리, 당시의 관찰은 무엇인가?

제약:
  호환성, 비용, 시간, 보안, 운영, 권한, 바꾸지 못하는 결정은 무엇인가?

범위 밖:
  이번 작업에서 해결하지 않는 문제는 무엇인가?

결정 권한:
  AI가 결정할 수 있는 것과 소유자 확인이 필요한 것은 각각 무엇인가?
```

**고정 목적**은 항해의 목적지이고, **수단 가설**은 목적지로 갈 임시 항로다. 목적지는 명시적인 결정 없이는 바꾸지 않는다. 반대로 문장·형식·검사·생성기·역할·구조는 모두 수단이므로 증거에 따라 버릴 수 있다.

## 2. 판단의 위계

충돌할 때 위 항목이 아래 항목을 이긴다.

```text
1. 소유자가 명시한 목적·금지·우선순위
2. 이미 확정된 결정과 그 결정의 근거
3. 현재 상태에서 재현한 실패와 외부 도구의 실측
4. 설계·기술 가설
5. 구현 방법과 코드·산문 변경안
6. AI의 개선 제안
```

하위 항목이 상위 항목과 충돌하면 AI는 상위를 조용히 고치지 않는다. 충돌 좌표, 원인, 선택지, 결정에 필요한 증거를 보고한다. 구현의 편의성이나 AI의 자신감은 목적 변경의 근거가 아니다.

### 2.1 개선 과정의 원점 보존 검사

검증과 구현에서 새 사실이 나오면 먼저 **수단이 틀렸는지**와 **목적이 틀렸는지**를 분리한다. 수단이 반증되면 문장·구조·도구·검사를 바꾼다. 목적이나 금지를 바꿔야 한다면, 현재 구현을 계속하기 전에 소유자 결정으로 되돌린다.

```text
원래 해결하려던 사용자 문제:
보존해야 할 행동 변화와 금지:
현재 제안이 제거하는 기존 부담·실패:
현재 제안이 새로 만드는 부담·위험:
내부 지표가 아니라 종단 결과에서 좋아지는 것:
```

새 제안이 내부 정합성·test 통과·기술적 완성도를 높이더라도, 원래 문제를 줄이지 않거나 사용자의 총부담을 늘리면 개선이 아니다. 반대로 핵심 수단이 반증되어도 목적이 바로 실패한 것은 아니다. 가장 단순한 기준안으로 돌아가 다른 수단 가설을 연다.

## 3. 철학을 이름이 아니라 기능으로 쓴다

아래 철학들은 모든 단계에 똑같이 적용하는 만능 절차가 아니다. 서로 다른 종류의 모름을 다룬다.

| 기능 | 철학적 뿌리 | 이 체계에서 하는 일 | 적용하지 않는 경계 |
|---|---|---|---|
| 문제를 다시 발견 | 듀이의 탐구 | 막연한 불편·실패를 정식 문제 상황으로 바꾼다 | 이미 판정 가능한 기술 비교를 끝없이 다시 정의하지 않는다 |
| 정의·전제의 빈틈 노출 | 소크라테스의 엘렝코스 | 목적, 핵심 용어, 성공 조건, 전제와 반례를 명료화한다 | 기술 후보의 성능·보안 우열을 대화만으로 고르지 않는다 |
| 과거 실패를 읽기 | 해석학적 순환 | 전체 목적 가설과 과거 자료의 부분 증거를 왕복하며 읽는다 | 과거 결정·구조를 현재의 진실 또는 의무로 취급하지 않는다 |
| 경쟁 해법 만들기 | 퍼스의 귀추 | 하나의 수리가 아니라 서로 다른 원인·수단 가설을 만든다 | 가설을 증거나 결정으로 부르지 않는다 |
| 가설 가르기 | 포퍼의 비판적 시험 | 시작 전에 가설을 버리게 할 관찰을 정한다 | 한 실패만으로 전체 설계·목적을 기계적으로 폐기하지 않는다 |
| 파급과 소유자 찾기 | 시스템 사고 | 문제·정보·수정이 흐르는 경로와 2차 효과를 본다 | 모든 문제를 거대한 시스템 재설계로 키우지 않는다 |
| 불완전한 정보에서 약속 | 아리스토텔레스의 프로네시스 | 지금 확정할 것과 더 알아볼 것을, 되돌림 비용까지 보고 고른다 | 경험·직감을 근거 없는 권위로 쓰지 않는다 |
| 만들며 배우기 | Schön의 행동 중 성찰 | 구현·표현물이 드러낸 뜻밖의 사실로 수단 가설을 고친다 | 구현 중 목적과 범위를 조용히 바꾸지 않는다 |
| 반복 실패에서 상위 전제 재검토 | Argyris의 이중고리 학습 | 행동뿐 아니라 목표·규칙·가정도 다시 볼지 판단한다 | 매 작업마다 회고·재설계를 의무화하지 않는다 |

이 표가 뜻하는 바는 단순하다. **소크라테스는 문제를 선명하게 하고, 듀이는 문제 상황을 만들며, 퍼스는 가능한 설명을 늘리고, 포퍼는 그것을 줄이며, 시스템 사고는 고칠 위치를 찾고, 프로네시스는 언제 충분한지 판단한다.** 어느 하나도 전체 절차를 대체하지 않는다.

## 4. 세 모드와 전체 흐름

이 체계는 상황에 따라 세 모드로 쓴다. 모든 작업이 처음부터 전체 흐름을 밟지 않는다.

```text
A. 기반 기획 모드
   과거 실패 재구성 → 문제 재정의 → 경쟁 설계 가설 → 가능성 판별 → 첫 구현 단위

B. 점진 구현 모드
   고정 계약 → 최소 구현 → 반례·효과 검증 → 올바른 층으로 환류 → 다음 단위

C. 늪 탈출 모드
   증식 신호 → 확장 동결 → 원인 재배치 → 독립 반증 → 최소 충분 개입 또는 보류
```

```text
과거 실패 자료
       │
       ▼
실패 재구성 ── 사실 부족 ──▶ 미결정과 필요한 관찰을 기록
       │
       ▼
문제 상황·목적 명료화 ── 정의·전제 모순 ──▶ 소유자와 목적 확인
       │
       ▼
경쟁 가설 생성 ──▶ 예측·판별 실험 ──▶ 지원 / 반증 / 미결정
       │                                        │
       ▼                                        │
최소 구현 약속 ◀───────────────────────────────┘
       │
       ▼
구현 ── 뜻밖의 발견 ──▶ 구현 / 구조 / 전달 / 목적 중 소유 층 분류
       │                                            │
       ▼                                            ▼
검증 ── 계약 판정 + 효과 판정 ───────────────▶ 해당 층으로 환류
       │
       └─ 반복 실패·증식 신호 ──▶ 늪 탈출 모드
```

되돌아감은 실패가 아니다. 잘못된 층에서 계속 수리하는 것이 실패다.

### 4.1 비례성 게이트 — 비용이 아니라 결정 가치로 깊이를 정한다

**과잉**은 카드·에이전트·검사 수가 많다는 뜻이 아니다. 비용이 들어도 그 관찰이 큰 잘못된 결정을 막거나, 여러 번의 수리·재검증을 한 번의 판별로 대체한다면 충분히 실용적이다.

반대로 다음이 참이면 과잉이다.

> 이 절차의 어느 결과가 나와도 현재 결정·행동·범위가 바뀌지 않거나, 바뀌는 위험보다 절차의 읽기·실행·유지 비용이 더 크다.

탐구·검증·교차 반증을 열기 전에 아래 다섯 줄을 쓴다.

```text
걸린 결정:
  이 관찰 뒤에 실제로 채택·기각·보류할 결정은 무엇인가?

가장 큰 미지:
  지금 틀리면 되돌림 비용이 큰 가정은 무엇인가?

결과별 행동:
  지원 / 반증 / 미결정 각각에서 무엇을 다르게 할 것인가?

가장 싼 충분 관찰:
  이 결정을 가를 최소 실행·원문 대조·실제 흐름은 무엇인가?

비용 경계:
  이 관찰의 시간·문서·기계 비용이 피하려는 수리·장애·결정 잠금 비용보다 작은 이유는 무엇인가?
```

`결과별 행동`이 같은 경우에는 검증하지 않는다. 이미 정한 행동을 정당화하기 위한 의식이기 때문이다. 대신 그 사실을 “현재는 결정이 아니라 실행의 문제”로 적고 가장 작은 구현·확인을 한다.

### 4.2 세 깊이 중 필요한 것만 연다

모든 작업에 전체 체계를 읽히지 않는다. 불확실성·되돌림 비용·파급 범위가 커질수록 깊이를 올리고, 판정 뒤에는 즉시 다시 낮춘다.

| 깊이 | 여는 조건 | 필요한 것 | 열지 않는 것 |
|---|---|---|---|
| 1. 국소·되돌릴 수 있음 | 하나의 소유자 안에서, 기존 계약과 검증 경로가 명확함 | 작업 맥락의 고정 목적·반례·최소 확인 | 과거 재구성, 경쟁 가설, 독립 반증 |
| 2. 불확실한 선택 | 수단의 가능성·비용·품질 중 하나가 미지이거나 둘 이상의 후보가 실제로 갈림 | 탐구 카드, 경쟁 가설, 가장 싼 판별 | 전체 실패 역사, 광범위한 시스템 재설계 |
| 3. 기반·고위험 변화 | 목적·의미 계약·전달 구조·여러 소유자에 걸치거나 과거 실패가 반복됨 | 실패 재구성, 문제 명료화, 파급 지도, 독립 반증 | 증거 없이 바로 구현하거나 한 카드에 여러 결정을 묶기 |

깊이 3이 더 신중해서 항상 좋은 것이 아니다. 같은 목적을 지키는 국소·되돌릴 수 있는 변화에 깊이 3을 쓰면, 절차 자체가 새 장애물이 된다. 반대로 전달 구조나 의미 계약처럼 한 변경이 많은 AI 행동을 바꿀 수 있는 곳에서 깊이 1만 쓰면, 빠르게 보이지만 여러 번의 수리로 비용을 되갚는다.

### 4.3 전체 시야는 ‘전체 분석’이 아니라 ‘경계 횡단 확인’이다

전체를 보라는 말은 매 작업마다 거대한 지도와 모든 연관성을 만들라는 뜻이 아니다. 변경이 아래 경계 중 둘 이상을 건너거나, 한 경계 안에 있어도 조용한 데이터 손실·보안·불가역 변경처럼 높은 위해를 만들 수 있을 때만 그 경로를 한 줄씩 걷는다.

```text
의도·결정 → 저작물 → 생성·전달 → AI·사용자 행동 → 실제 효과 → 다음 피드백
```

각 경계에서 “입력은 무엇이고, 출력은 무엇이며, 누가 소유하고, 무엇이 소실·왜곡될 수 있는가?”만 적는다. 한 경계 안에 머무는 국소 변경에는 이 지도를 만들지 않는다. 이것이 전체 시야와 절차 과잉을 동시에 피하는 최소 단위다.

### 4.4 검증의 폐쇄 계약 — 새 발견이 현재 작업을 무한히 삼키지 못하게 한다

검증을 시작하기 전에 아래를 고정한다.

```text
이번에 공격할 주장:
이번 결과가 바꿀 결정:
이번 검증의 성공·실패 조건:
이번 범위 밖:
새 발견을 현재 작업에 편입할 조건:
종료 조건:
```

새 발견은 다음 둘 중 하나일 때만 현재 작업을 다시 연다.

```text
1. 현재 검증 대상의 결론을 직접 뒤집는 구체적 실패 경로가 있다.
2. 현재 변경이 새로 만든, 조용한 데이터 손실·보안·불가역 손상 같은 높은 위험의 경로가 있다.
```

그 외의 발견은 위치·관찰·재개 조건만 남기고 별도 관찰로 분리한다. 발견하지 못한 문제가 없다는 뜻은 아니지만, 현재 결정을 바꾸지 않는 모든 우려를 같은 수리·검증 루프에 넣어 끝없이 확장하는 것을 막는다.

검증은 아래 중 하나가 참이면 닫는다.

```text
- 사전에 정한 주장과 반례 경로를 충분히 걸었고, 결과가 현재 결정을 바꾸지 않는다.
- 결과가 결정을 바꾸어 올바른 소유 층으로 환류했다.
- 판정에 필요한 관찰이 없으며, 필요한 외부 상태·측정·소유자 결정이 명시되었다.
```

새로운 주제를 계속 찾지 않는 것은 검증 누락이 아니라, 현재 주장에 대한 검증과 다음 주장에 대한 탐구를 분리하는 방식이다.

### 4.5 실행 전 논리 시나리오 검증

큰 탐구·기반 변경·독립 반증을 시작하기 전에는 코드를 더 쓰지 말고 아래 네 결과를 한 번씩 걷는다.

```text
지원됨:
  가설이 관찰을 견디면 무엇을 채택하고 무엇을 하지 않는가?

반증됨:
  가설이 깨지면 정확히 어느 소유자와 어느 질문으로 돌아가는가?

혼합됨:
  일부 조건에서만 성립하면 무엇을 분리하고, 무엇을 보류하는가?

미결정:
  관찰이 부족하면 어떤 결정을 하지 않으며, 무엇이 다시 열 조건인가?
```

네 결과 중 하나라도 다음 행동을 말할 수 없으면, 아직 실행할 탐구가 아니라 기획의 빈칸이다. 이 사전 걷기는 철학적 장식이 아니라, 검증 뒤에 즉흥적으로 예외·규칙·새 작업을 만들어 루프를 늘리는 실패를 막는 논리 검사다.

### 4.6 책임의 완전성 — 기능 목록보다 소유 경계를 먼저 닫는다

이 방법의 완전성은 발생 가능한 모든 예외와 단계를 미리 열거하는 데 있지 않다. 다음 책임이 빠지거나 중복 소유되지 않게 하는 데 있다.

| 책임 | 기본 소유자 | 핵심 질문 |
|---|---|---|
| 목적·배경 | 사람에게 읽히는 자연어 | 왜 하며 무엇을 바꾸면 안 되는가? |
| 관찰 | 도구 또는 출처가 있는 기록 | 무엇을 실제로 보았는가? |
| 의미 판단 | AI와 필요한 경우 사람 | 관찰이 현재 목적에서 무엇을 뜻하는가? |
| 결정 가능한 계산 | 선언·코드·스키마·검사 | 같은 입력에서 같은 답을 낼 수 있는가? |
| 정확한 작성·렌더링 | renderer·template | 뜻이 정해진 뒤 형식과 반복을 기계가 맡을 수 있는가? |
| 지속 상태 | 최소한의 durable artifact | 다음 행동·재개·동시성 때문에 실제로 기억해야 하는가? |
| 실제 효과 | 사용자·host·외부 시스템 | 최종 행동과 영향은 어디에서 일어나는가? |
| 증거·환류 | 검사와 관찰 기록 | 무엇을 확인했고 어느 결정으로 되돌아가는가? |

한 책임에 정본이 둘이면 충돌이 생기고, 아무 소유자도 없으면 AI가 빈칸을 추측한다. 새 기능을 논의할 때는 기능 이름을 먼저 늘리지 말고, 이 표에서 어느 책임이 비어 있으며 기존 소유자가 왜 충분하지 않은지 먼저 찾는다.

## 5. 기반 기획 모드 — 실패한 과거에서 새 기획으로

### 5.1 과거 실패는 규칙이 아니라 재료다

과거의 코드, 문서, 수리안, 실패 기록에는 두 위험이 있다. 무시하면 이미 치른 비용을 다시 치르고, 그대로 믿으면 과거의 임시 선택을 불변식으로 보존한다.

해석학적 순환은 이 둘 사이의 방법이다. 먼저 전체 목적에 대한 잠정 가설을 세우고, 과거 자료의 부분을 그 가설로 읽는다. 부분이 가설과 맞지 않으면 전체 가설을 고치고 다시 읽는다. 전체와 부분을 왕복하되, 어느 쪽도 처음부터 확정하지 않는다. [3]

각 과거 실패는 아래처럼 재구성한다. 이 기록은 별도 파일을 무조건 만들라는 뜻이 아니다. 한 작업 기록의 한 구역으로도 충분하다.

```text
실패 장면:
  누가, 어떤 입력·맥락에서, 무엇을 하려 했고 실제로 무엇이 일어났는가?

영향:
  어떤 목적·사용자 행동·유지보수성·비용이 손상되었는가?

관찰된 사실:
  원문 좌표, 실행 결과, 생성물, 대화·사용 흐름 중 실제로 본 것은 무엇인가?

과거 수리:
  무엇을 바꿨고, 어떤 효과가 있었고, 무엇을 확인하지 못했는가?

해석 가설:
  가능한 원인은 무엇인가? 이것은 아직 사실이 아님을 명시한다.

재개 조건:
  어떤 새 관찰이 이 해석을 지지·반박하거나 다시 열게 하는가?
```

이 단계의 완료는 원인 확정이 아니다. 과거 실패를 “이미 아는 사실”, “해석”, “미검증”으로 분리해, 새 기획이 과거의 두려움이나 과거 수리안에 종속되지 않게 하는 것이다. 한 작업·도구에서 얻은 실패를 다른 작업·도구에 옮길 때는, 실패의 인과 경로·행위자·제약·관찰 조건이 실제로 같은지 먼저 대조한다. 하나라도 다르면 그 실패는 다른 곳의 규칙 근거가 아니라 조사할 가설이다.

#### 실패한 체계를 처음부터 다시 설계할 때

기존 계획 자체가 실패했다고 판정한 greenfield 재구성에서는 과거 구현을 개선 대상이나 호환 기준선으로 암묵적으로 남겨 두지 않는다.

```text
새 설계에 먼저 들어올 수 있는 것:
  확인된 사용자 목적, 실제 실패 장면, 구속력 있는 외부 계약, 검증된 불변식

바로 들어올 수 없는 것:
  과거 단계 이름, 상태 기계, 파일 구조, API, 테스트 기대값, 임시 수리안, 이미 구현했다는 사실
```

과거 구현은 읽기 가능한 참고 영역에 격리하고, 새 목적에서 가장 작은 수직 흐름을 독립적으로 설계한다. 그 흐름과 판정 기준이 생긴 뒤에만 과거 자료를 대조하여 누락된 실제 요구나 반례를 찾는다. 과거 코드를 복사하거나 호출하려면 “이미 존재한다”가 아니라 현재 설계의 유일한 소유자로 채택할 독립 근거가 있어야 한다. 이 규칙은 과거의 학습을 버리지 않으면서도 실패한 구조가 새 설계를 선점하는 것을 막는다.

### 5.2 문제 상황을 먼저 만든다

듀이의 탐구에서 문제는 처음부터 완성된 질문이 아니다. 불확정적이고 불편한 상황을, 조사·가설·행동을 통해 더 정해진 상황으로 바꾸는 과정에서 문제가 생긴다. [4]

기획 초입에서는 해결안을 묻지 말고 아래를 작성한다.

```text
현재 상황:
  어떤 흐름이 누구에게 어떤 불확실성·비용·오류를 만들고 있는가?

원하는 변화:
  그 상황이 어떻게 달라지면 가치가 생기는가?

핵심 긴장:
  동시에 만족하기 어려운 가치·제약은 무엇인가?

문제 아닌 것:
  불편해 보이지만 현재 목적·증거상 해결 대상으로 삼지 않는 것은 무엇인가?
```

`문제 아닌 것`은 과잉을 막는 핵심 필드다. 단순히 비슷한 구조이거나 AI가 이해하기 어려워 보인다는 이유만으로 문제를 발명하지 못하게 한다.

### 5.3 소크라테스식 명료화의 정확한 사용

엘렝코스는 답을 생성하는 장치가 아니라, 주장 속 정의·전제·반례를 드러내는 대화다. 대화의 좋은 종점은 때때로 “아직 결정할 수 없다”이다. [5]

다음 대화는 기획의 제품·기술 목적을 선명하게 하는 데만 쓴다.

```text
주장: “AI가 이 규칙을 항상 지켜야 한다.”

질문:
  여기서 ‘항상’은 어떤 사용자·입력·실행 맥락까지 뜻하는가?
  지켜졌다고 관찰할 수 있는 행동은 무엇인가?
  이 규칙이 다른 고정 목적과 충돌하는 사례는 없는가?
  어떤 반례가 나오면 규칙이 아니라 정의·목적을 다시 봐야 하는가?
  이 요구는 원하는 행동인가, 아니면 과거 수리안을 다시 말한 것인가?
```

이 질문 뒤에 나와야 할 산출물은 “더 많은 질문”이 아니라 하나의 **문제 주장**이다.

```text
문제 주장:
  <대상>이 <상황>에서 <원하는 행동>을 하지 못해 <영향>이 생긴다.

성공 조건:
  <관찰 가능한 결과>가 <조건>에서 나타나야 한다.

반례:
  <이 결과>가 나오면 현재 문제 정의 또는 수단 가설을 다시 본다.
```

### 5.4 경쟁 가설로 더 나은 문제와 설계를 도출한다

한 문제에 첫 번째로 떠오른 수리안을 바로 탐구 카드의 가설 A로 놓으면 AI의 시야는 처음부터 좁아진다.

퍼스의 귀추는 관찰을 가장 잘 설명할 수 있는 가설을 만드는 추론이다. 실무에서는 아래 세 가설을 강제로 분리해, AI가 다른 원인 위치를 보게 만든다. [1]

```text
H1. 국소 원인 가설
    현재 보이는 구성물 또는 구현이 직접 원인이다.

H2. 상위 계약·전달 가설
    목적, 의미 계약, 정보 전달, 소유 경계 중 하나가 원인이다.

H3. 비문제 또는 외부 조건 가설
    관찰이 불완전하거나, 현재 목적상 고칠 문제가 아니거나, 통제 밖 조건이 원인이다.
```

각 가설은 아래를 갖지 않으면 후보가 아니다.

```text
가설이 설명하는 사실:
가설이 설명하지 못하는 사실:
가설이 맞다면 추가로 관찰되어야 할 것:
가설을 가장 싸게 가를 실험:
가설이 채택되면 사라져야 할 기존 복잡성:
```

세 가설은 정답 개수를 늘리려는 형식이 아니다. “현재 코드 고치기”만 보는 AI에게 목적·전달·비문제 가능성을 같은 출발선에 올리는 장치다. 제약상 한 가설만 가능하다는 증거가 있으면 나머지를 억지로 만들지 않는다.

### 5.5 시스템 경계와 파급 지도

시스템 사고는 모든 것을 거대하게 그리라는 방법이 아니다. 문제를 고치기 전에 최소한 아래의 인과 경로를 한 번 걷는 방법이다.

```text
의도·결정의 출처
→ 저작된 산문 또는 구현
→ 생성·전달·배포 경로
→ AI 또는 사용자의 해석·행동
→ 사용자·운영 효과
→ 관찰·피드백이 다음 결정으로 돌아오는 경로
```

각 화살표에서 “무엇이 변형·소실·지연·왜곡될 수 있는가?”를 묻는다. Meadows의 시스템 관점은 목표, 정보 흐름, 피드백 고리, 규칙이 국소 수치 조정보다 더 강한 개입점일 수 있음을 보여 준다. [6]

이 지도는 새 다이어그램을 의무화하지 않는다. 변경이 한 화살표를 건널 때만, 그 화살표의 실제 입력·출력·소유자를 기록하면 된다.

### 5.6 기술 기획 완료 조건

다음이 되면 전체를 한 번에 설계하지 않고도 첫 구현을 시작할 수 있다.

```text
- 고정 목적과 범위 밖이 명시되었다.
- 과거 실패가 사실·해석·미검증으로 분리되었다.
- 문제 주장과 성공·반례 조건이 있다.
- 가장 위험한 미지에 경쟁 가설과 판별 계획이 있다.
- 첫 구현 단위가 하나의 계약과 하나의 판정만 가진다.
- 실패 시 구현·구조·전달·목적 중 어디로 돌아갈지 정해졌다.
```

## 6. 기술 탐구와 결정

### 6.1 언제 탐구를 여는가

다음 중 하나가 참이면 구현 전에 탐구 단위를 만든다.

- 후보 수단이 실제 제약에서 작동하는지 모른다.
- 성능·안전·호환성·운영성·이해 가능성처럼 충돌하는 성질이 있다.
- 실패 비용이 커서 실제 운영에서 처음 배우기 위험하다.
- 도구 문서·기존 성공 사례가 현재 조건을 보장하지 않는다.

반대로 제약과 검증된 경로가 충분히 명확하면 탐구를 위한 탐구를 만들지 않는다.

### 6.2 기술 탐구 카드

```text
질문:
  정확히 무엇이 가능한지, 불가능한지, 또는 더 나은지 모르는가?

고정 목적과 금지:
  이 탐구가 바꾸면 안 되는 것은 무엇인가?

현재 사실:
  추측이 아니라 이미 관찰한 사실은 무엇인가?

경쟁 가설:
  서로 다른 인과 위치 또는 수단을 가진 후보는 무엇인가?

예측:
  각 가설이 맞다면 어떤 결과·비용·실패 양상이 나와야 하는가?

판별:
  원문·문서 확인 → 축소 prototype → 대표 조건 실행 중
  가장 싸면서 후보를 가장 잘 가르는 관찰은 무엇인가?

판정선:
  어떤 결과면 지원 / 반증 / 미결정인가?

결과:
  관찰 원문, 판정, 남은 미검증, 다음 결정 또는 다음 탐구.
```

포퍼식 적용은 “한 번 실패하면 전체를 버린다”가 아니다. 실패가 구현·환경·측정·목적 중 무엇을 바꾸는지 분류하게 하는 것이다. 가설을 시작하기 전에 버림 조건을 써야, 실패 후 임시 예외로만 가설을 보호하는 일을 막는다. [2]

### 6.3 핵심과 잠정 수단을 분리한다

기획에서 다음 두 층을 명시한다.

```text
핵심:
  소유자가 지키기로 한 가치, 외부 계약, 검증된 불변식.

잠정 수단:
  현재의 문장, 형식, 구조, 도구, 검사, 역할, 구현 방식.
```

과거에 오래 존재했다는 이유만으로 잠정 수단을 핵심으로 승격하지 않는다. 반대로 핵심을 바꾸려면 수단 실패보다 높은 수준의 근거와 소유자 결정이 필요하다. 이 구분은 실패한 구조를 “원칙”이라는 이름으로 보존하거나, 편한 구현을 “목적”으로 승격하는 양쪽 오류를 막는다.

### 6.4 결정의 종료

프로네시스는 모든 불확실성이 사라질 때까지 기다리는 태도가 아니다. 지금 행동할 만큼 충분한 증거와, 잘못되었을 때 되돌아갈 수 있는 경로를 함께 보는 판단이다. [7]

```text
지금 채택할 수 있는 이유:
아직 모르는 것:
미루는 비용:
지금 확정해 잠기는 비용:
되돌림 방법과 조건:
소유자 확인이 필요한 결정:
```

## 7. 점진 구현 모드

### 7.1 구현 카드

```text
고정 계약:
  이번 변경이 지켜야 하는 외부 행동·금지·호환성은 무엇인가?

구현 가설:
  이 변경이 계약을 만족시킬 것이라고 보는 이유는 무엇인가?

유일한 소유자:
  이 사실 또는 규칙을 고쳐야 하는 정본 위치는 어디인가?

영향 경계:
  어떤 산문, 코드, 생성물, 검사, 실제 흐름이 움직일 수 있는가?

반례:
  무엇이 나오면 구현 가설이 틀렸다고 볼 것인가?

최소 변경:
  확인된 원인을 없애는 가장 작은 의미상의 개입은 무엇인가?

되돌림:
  이 변경이 예상과 다를 때 무엇을 어떤 조건에서 되돌리거나 상위 결정으로 올릴 수 있는가?

검증:
  구조 / 전달 / 행동 / 효과 중 무엇을 무엇으로 보았는가?

미검증:
  이번 변경으로 말할 수 없는 것은 무엇인가?

환류:
  실패하면 어느 질문과 어느 소유자로 돌아가는가?
```

### 7.2 구현 중의 성찰은 목적 변경 권한이 아니다

Schön의 행동 중 성찰은 만들고 있는 산문·코드·표현물이 예상하지 못한 사실을 되돌려 줄 때, 그 사실로 수단 가설을 수정하는 태도다. [8]

```text
뜻밖의 발견
→ 현재 계약을 실제로 깨는가?
   ├─ 아니오: 기록하고 현재 단위를 계속한다.
   └─ 예: 발견이 구현·구조·전달·목적 중 어느 층을 흔드는지 분류한다.
           그 층의 탐구·결정으로 돌아간다.
```

“더 좋아 보인다”는 발견은 자동으로 현재 단위에 승격하지 않는다. 아래가 모두 참일 때만 승격한다.

```text
1. 고정 목적을 더 잘 만족한다는 직접 근거가 있다.
2. 기존에 무엇을 대체하거나 제거하는지 말할 수 있다.
3. 새 복잡성·운영 비용·검증 비용을 셌다.
4. 현재 작업의 경계를 조용히 넓히지 않는다.
5. 되돌림 또는 재검토 조건이 있다.
```

그렇지 않으면 발견은 기록하되 현재 단위를 끝낸다. 가능성은 항상 현재 작업을 중단시킬 권리가 있는 것이 아니다.

### 7.3 AI 작업면과 컨텍스트 경제성

스킬은 내부 모델이 정교한 것만으로 실용적이지 않다. 실제 AI가 한 작업을 시작하고, 판단하고, 결과를 넘기는 표면이 작고 명확해야 한다.

```text
입력:
  목적, 현재 대상, 사용 가능한 artifact, 권한, 지금 필요한 판단

작업 중:
  기계가 관찰·계산한 사실, AI가 답해야 할 하나의 의미 질문,
  답에 따라 달라지는 다음 행동

결과:
  수행한 행동, 바뀐 durable artifact, 근거, 미결정·미검증, 다음 소비자가 읽을 위치
```

컨텍스트 비용은 글자 수 하나로만 세지 않는다. 다음 항목을 기준안과 비교한다.

- 모든 호출에 항상 들어가는 고정 byte와 현재 조건에서만 읽는 조건부 byte
- AI가 기계에서 다시 베껴 적거나 계산해야 하는 중복 정보
- 한 판단을 끝내는 tool round-trip과 오류 복구 단계
- 이전 대화가 없으면 재구성할 수 없는 숨은 상태
- 내부 기계를 이해시키기 위한 설명과 실제 도메인 판단에 필요한 설명의 비율

새 API·명령·문서·중간 표현을 추가하려면 그것이 없애는 산문, 추론, 왕복 또는 복구 단계를 함께 말해야 한다. 내부 구조가 늘었더라도 AI의 고정 문맥과 판단 부담이 더 크게 줄어들 수는 있다. 반대로 AI가 같은 자연어 판단을 한 뒤 그 값을 기계에 다시 입력해야 하고 다음 행동도 스스로 조립한다면, 그 기계는 계산을 덜어 준 것이 아니라 의식을 하나 추가했을 가능성이 크다.

### 7.4 상태와 여러 세션의 입장 조건

상태는 workflow가 있어 보이게 하는 장치가 아니다. 다음 행동을 바꾸거나, 중단 뒤 재개를 가능하게 하거나, 여러 작업의 충돌을 막을 때만 저장한다.

```text
저장할 후보:
  작업 식별자, 입력 artifact revision, 승인·결정, 완료 효과의 증거, 다음 행동을 바꾸는 최소 좌표

저장하지 않을 후보:
  대화에서 다시 추론할 수 있는 설명, AI의 임시 생각, 모든 단계를 위한 전역 current 상태,
  실제 행동 없이 진행된 것처럼 보이게 하는 표식
```

동시 실행 가능성이 있는 환경에서는 하나의 전역 `current task`를 진실로 두지 않는다. 상태는 가능한 한 task와 artifact별로 분리하고, 쓰기에는 읽었던 revision 또는 동등한 전제 증거를 붙인다. 전제가 바뀌었으면 조용히 덮거나 자동 병합하지 않고 충돌을 드러내 다시 판단하게 한다. 완료 상태도 플래그 하나가 아니라 실제 효과나 결과 artifact의 근거와 연결한다.

상태를 추가하기 전에 “이 값이 없을 때 어떤 다음 행동·재개·동시성 실패가 생기는가?”에 답할 수 없으면 저장하지 않는다.

### 7.5 정확한 작성과 renderer의 경계

AI가 의미를 이미 판단한 뒤 정확한 양식, 반복 구역, 번호, 링크, metadata를 다시 기억해 작성하게 할 필요는 없다. 구조가 결정 가능하면 AI는 의미 필드만 제출하고 renderer가 정확한 결과를 만든다.

```text
AI가 소유:
  목적, 주장, 근거의 의미, 열린 판단, 예외 설명처럼 해석이 필요한 내용

기계가 소유:
  필수 필드, 허용 값, 순서, 반복, 기본값, 경로, 식별자, 참조와 렌더 형식
```

기계는 필드의 존재·형식·관계를 검증할 수 있지만, 자연어 내용이 진실인지 충분한지는 자동으로 증명하지 못한다. 반대로 자유로운 판단 문장까지 작은 필드로 분해하면 AI가 형식 채우기에 집중하고 의미 연결을 잃는다. 따라서 renderer의 입장 조건은 “같은 의미 입력에서 원하는 출력 형태를 결정적으로 만들 수 있고, AI가 외워야 할 형식이나 반복을 실제로 제거한다”이다.

## 8. 검증: 계약, 전달, 행동, 효과를 분리한다

AI가 읽는 스킬과 그 도구에서는 아래 네 면을 같은 것으로 부르면 안 된다.

```text
의미:
  산문·구조가 AI에게 어떤 판단과 행동을 요구하는가?

전달:
  저작 원문이 생성·렌더·배포·실행 문맥까지 손실 없이 도달하는가?

행동:
  깨끗한 AI 또는 실제 사용 흐름이 원하는 행동을 하는가?

효과:
  그 행동이 원래의 사용자·운영 문제를 실제로 줄이는가?
```

```text
소스 검토 통과       ≠ 전달됨
생성·hash 통과        ≠ AI가 이해함
렌더 출력 확인        ≠ 실제 AI가 행동함
한 번의 행동 성공     ≠ 조건 전체에서 안전함
```

검증은 두 판정을 함께 낸다.

```text
계약 판정:
  정한 기능·안전·전달·복구 성질을 깨는 반례가 있는가?

효과 판정:
  계약이 통과했더라도 원래 문제는 실제로 더 나아졌는가?
```

테스트·생성 검사·정적 분석은 강력하지만, 각자가 주장할 수 있는 범위를 넘지 못한다. 프로그램 테스트는 일반적으로 결함의 존재를 드러내는 데 강하고, 결함의 부재 전체를 증명하지는 못한다. [9]

AI 행동을 검증할 때는 가능하면 같은 입력·같은 성공 기준·동일한 작업 조건에서 **기준안과 변경안**을 비교한다. 한 번의 장문의 대화는 이해의 증거가 아니다. 최소한 서로 다른 깨끗한 문맥에서 실제로 어떤 다음 행동이 나왔는지를 관찰하고, 결과가 달라진 조건을 기록한다.

검증 보고는 아래 다섯 줄을 남긴다.

```text
무엇을 공격했는가:
어떤 관찰로 버텼는가:
어느 면(의미·전달·행동·효과)을 확인했는가:
다음에 다시 볼 조건:
미검증:
```

### 8.1 사람과 대화하고 결과를 설명할 때: 사람말 교정

AI가 기획·조언·문제 분석·완료 보고를 할 때의 언어와, 실행을 정확히 지시하는 문장은 같은 방식으로 쓰지 않는다. 전자는 사람이 판단할 수 있도록 **생각의 경로를 드러내는 자연어**여야 한다. 어린이 수준으로 내용을 축소하거나 비유로 바꾸라는 뜻이 아니다. 전문 용어와 복잡한 판단은 유지하되, AI가 압축한 명사 묶음이나 자체 관리 용어 때문에 사람이 추론해야 하는 부분을 없앤다.

대화와 결과 보고에는 다음 교정 패스를 적용한다.

```text
1. 먼저 결론 또는 현재 판단을 한 문장으로 말한다.
2. 이어서 무엇을 보았고, 그래서 왜 그 판단을 했는지 쓴다.
3. 한 문장에는 판단·근거·예외·다음 행동 중 하나만 주로 맡긴다.
4. 새 이름을 붙여야 할 구분이면, 이름보다 먼저 평범한 문장으로 그 현상을 설명한다.
5. 정확한 기술 용어는 남기되, 바로 뒤에 실제 상태·행동·영향을 적는다.
6. 비유는 문자 설명 뒤에만 보조로 쓴다. 비유가 규칙의 정본이 되면 안 된다.
7. 사실, 해석, 제안, 미확인을 섞어 확정처럼 말하지 않는다.
```

교정할 때 특히 `이것`, `그 과정`, `정합성`, `환류`, `적절히`, `필요한 범위`처럼 읽는 사람이 앞 문맥을 다시 추측해야 하는 말을 찾는다. 삭제가 목적은 아니다. 그 말이 가리키는 대상·조건·행동을 문장 안이나 바로 앞에 밝혀, 처음 읽는 사람도 다음 행동을 알 수 있게 하는 것이 목적이다.

```text
압축된 표현:
  "상위 판단을 보존해 국소 수정의 증식 가능성을 차단한다."

사람말 교정:
  "검증 결과가 기존 결정을 깨면, 현재 문장에 예외를 더하지 말고 그 결정을 다시 검토한다.
  그래야 같은 문제를 여러 문장과 검사에서 반복해 막지 않게 된다."
```

권고·결정·문제 설명처럼 사람이 선택해야 하는 출력은 가능하면 아래 순서를 따른다. 짧은 답변에 모든 줄을 억지로 넣지 않는다.

```text
현재 판단:
근거가 되는 관찰:
선택하면 달라지는 점:
아직 확인하지 못한 점 또는 다음 확인:
```

### 8.2 다른 AI도 읽는 저작물: 자연어의 해석 안정성

자연어만으로 서로 다른 모델, 서로 다른 이전 문맥, 서로 다른 추론 성향을 가진 AI가 **완전히 같은 뜻으로 읽게 보장할 수는 없다.** 문장을 더 길게 쓰거나 규칙을 더 많이 붙여도, 누락된 도메인 지식·모델의 능력 차이·숨은 문맥까지 전달할 수는 없다. 따라서 목표는 `모든 해석을 제거`하는 것이 아니라, **행동을 바꾸는 해석 차이를 줄이고 발견 가능하게 만드는 것**이다.

이를 위해 한 내용을 세 역할로 나눈다. 같은 사실을 세 곳에 반복하라는 뜻이 아니다. 각 역할의 정본을 하나만 둔다.

```text
1. 목적과 배경 — 왜 이 판단·기능이 필요한가, 무엇이 성공이며 무엇은 범위 밖인가.
   사람에게 읽히는 자연어가 소유한다.

2. 행동 계약 — 어떤 조건에서 누가 무엇을 하고, 어떤 결과로 끝나는가.
   행동이 달라질 수 있는 문장에만 짧고 일정한 조건 → 주체 → 행동 → 결과 → 경계를 쓴다.

3. 결정 가능한 사실 — 상태값, 허용 값, 순서, 경로, 계산, 생성 규칙처럼
   같은 입력이면 같은 판정이 가능한 내용.
   가능한 경우 선언·스키마·코드·검사 중 하나가 소유한다. 자연어는 그 기계의 목적과 사용 맥락만 설명한다.
```

2번은 모든 문장을 양식으로 만들라는 요구가 아니다. 배경 설명, 선택 이유, 열린 판단에는 자연스러운 문장이 더 낫다. 반면 아래 중 하나가 참인 문장은 행동 계약 또는 결정 가능한 사실로 승격한다.

```text
- 다르게 읽으면 상태 변경, 실행 순서, 외부 효과, 승인 여부, 성공 판정이 달라진다.
- 값·경로·형식·시점이 정확해야 하며 이미 기계로 판정할 수 있다.
- 같은 모호함이 실제로 두 번 이상 재발했고, 원인이 문장 자체의 행동 경계에 있다.
```

그 외에는 새 문법이나 선언 층을 만들지 않는다. 사용자가 고려한 DLC 같은 별도 선언 층도, 반복되는 행동 차이를 더 작고 명확한 정본으로 없애고 그 운용 비용을 감당할 수 있을 때만 가치가 있다. 사람에게 읽히는 배경까지 선언 언어로 옮기거나, 선언을 설명하는 새 장문의 산문을 만들면 문제를 옮긴 것뿐이다.

행동 계약에는 EARS의 가벼운 구조를 참고할 수 있다. 이 방법은 조건과 사건, 주체의 응답을 늘 같은 순서로 두어 자연어 요구사항의 모호성·복잡성을 줄이려는 방식이다. 그러나 이것은 요구사항 문장용 도구이지, 기획의 배경·철학·판단 이유 전체를 쓰는 언어는 아니다. [11]

```text
자유 산문:
  "상황을 고려해 필요하면 이전 결정을 다시 본다."

행동 계약:
  "새 관찰이 현재 결정의 성공 조건을 직접 반증하면,
  담당자는 현재 수정에 예외를 추가하지 않고 그 결정을 재검토 단계로 되돌린다."

결정 가능한 사실(필요할 때만):
  재검토 전이 조건과 상태값은 선언 또는 코드 한 곳에 둔다.
```

### 8.3 해석 차이를 다루는 최소 검증

새 문장이나 수정이 다른 AI의 행동을 바꿀 수 있을 때만, 문장 자체를 길게 비평하지 말고 짧은 해석 시험을 한다.

```text
1. 작성자는 이 문장이 요구하는 조건, 행동, 적용하지 않는 경계, 성공 증거를 적는다.
2. 깨끗한 문맥의 읽는 AI는 작성 의도를 보지 않고, 원문과 필요한 최소 문맥만 보고
   "언제 무엇을 해야 하는가 / 언제 하지 않아야 하는가 / 무엇을 알 수 없는가"를 답한다.
3. 두 결과가 행동에서 다르면, 먼저 누락된 배경·조건·소유자 중 무엇이 원인인지 찾는다.
4. 정확한 사실이 원인이라면 그 사실을 선언·스키마·검사로 옮긴다.
   판단이나 가치 충돌이 원인이라면 목적·우선순위·범위 밖을 자연어로 보완한다.
5. 같은 행동을 말한다면 표현 취향 차이는 결함으로 승격하지 않는다.
```

서로 다른 두 AI가 같게 답한 것은 보증이 아니라 관찰 하나다. 반대로 다르게 답한 것도 즉시 규칙을 늘릴 근거는 아니다. 차이가 실제 다음 행동·외부 효과·승인 판정에 영향을 주는지 먼저 확인한다. 이 시험의 목적은 문장 품평이나 모델 다수결이 아니라, **해석 차이가 제품 행동으로 번지는 경로를 찾는 것**이다.

문장이 세 번째 다듬기에도 같은 혼동을 만든다면 더 매끄럽게 고치려 하지 않는다. 다음 셋 중 무엇이 빠졌는지 판정한다.

```text
- 아직 결정되지 않은 목적 또는 우선순위
- 행동의 적용 조건·종료 조건·소유자
- 자연어가 소유하기 부적합한 결정 가능한 사실
```

그 뒤에만 목적 결정을 다시 열거나, 행동 계약으로 재작성하거나, 최소 선언 층을 만든다. 이것이 자연어 수정이 끝없이 늘어나는 루프를 끊는 기준이다.

### 8.4 테스트는 점수표가 아니라 결정 도구다

테스트 하나는 최소한 다음을 설명해야 한다.

```text
공격하는 주장:
근거가 된 실제 실패·요구·위험:
관찰하는 면: 의미 / 전달 / 행동 / 효과
실패하면 바뀌는 결정 또는 소유자:
적용 범위와 종료 조건:
대체·제거되면 함께 폐기할 조건:
```

이 정보를 말할 수 없는 테스트는 추가하지 않는다. 모든 내부 분기와 helper를 조회하는 것이 신뢰성은 아니다. 결정 가능한 계산에는 빠른 단위 검사가 적합하고, 전달에는 생성·설치·routing 확인이 적합하며, AI 행동에는 깨끗한 문맥의 대표 시나리오가 적합하고, 실제 효과에는 사용자·운영 관찰이 필요하다. 한 종류의 테스트가 다른 층의 증거를 대신하지 않는다.

검증 강도는 변경된 주장과 위해에 비례한다. release 또는 “완성도”라는 이름만으로 모든 과거 검사를 반복하지 않고, 현재 주장을 깨뜨릴 대표 경로를 선택한다. 통과 수·coverage·내부 상태의 완벽한 재현은 보조 지표일 뿐 제품 점수가 아니다. 테스트를 통과시키기 위해 목적이나 실제 AI 사용성을 약화해야 한다면 테스트의 소유 주장부터 다시 본다.

## 9. 늪 탈출 모드 — 원인 이전과 증식 차단

### 9.1 원인 이전 원칙

증상이 보이는 위치와 원인이 있는 위치는 다를 수 있다. 그러나 “더 상위에서 고치자”도 증거 없는 추측일 수 있다. 목표는 가장 추상적인 원인이 아니라, 같은 실패 종류를 설명하고 제거할 수 있는 가장 가까운 충분 원인을 찾는 것이다.

```text
관찰된 실패:
현재 재현:
직접 경로:
국소 / 상위 계약 / 비문제·외부 조건 가설:
각 가설이 참일 때 설명해야 할 다른 현상:
가장 싼 판별:
확인되면 고칠 유일한 소유자:
```

### 9.2 새 장치의 입장권

새 규칙·문서·검사·역할·예외·코드를 추가하려면 다음 네 질문에 답한다. 출발점은 현재 재현한 실패만이 아니라, 소유자가 명시한 요구나 실제로 적용되는 외부 제약일 수도 있다. 후자의 경우에도 “무엇이 요구되며, 지키지 않으면 어떤 구체적 위해가 생기는가”를 증거와 함께 써야 한다.

```text
1. 어떤 현재 실패 또는 구속력 있는 요구·외부 제약을 다루는가?
2. 그 실패 또는 위해는 이 장치 없이는 왜 다시 발생하거나 허용될 수 없는가?
3. 기존 장치 중 무엇을 대체하거나 단순화하는가?
4. 이 장치의 사용법·복구법·검증 비용은 장치가 막는 위험보다 작은가?
```

답할 수 없으면 추가하지 않는다. 제안은 관찰 또는 미래 탐구로 남긴다.

### 9.3 증식 신호와 즉시 행동

다음 중 하나가 보이면 더 많은 수리를 멈추고 문제의 프레임을 다시 잡는다.

```text
- 같은 문장·규칙·구조를 세 번째 고치고 있다.
- 예외·설명·검사만 늘고 새 행동 증거가 없다.
- 하나의 증상을 여러 표면에서 동시에 막고 있다.
- 한 AI의 실수를 모든 사용자·상황의 규칙으로 만들려 한다.
- 새 기계의 매뉴얼이 대체하려던 산문보다 커졌다.
- “혼동할 수 있다” 외에 구체적 실패 장면을 말할 수 없다.
- 통과한 검사 또는 과거 결정을 현재 목적보다 높은 권위로 쓰고 있다.
```

그때의 행동은 새 규칙을 추가하는 것이 아니다.

```text
1. 현재 사실, 해석, 결정, 추측을 분리한다.
2. 증거 없는 확장을 동결한다.
3. 문제가 시작된 상위 질문을 한 문장으로 다시 쓴다.
4. 경쟁 원인 두세 개와 판별 관찰 하나를 만든다.
5. 유일한 소유자를 다시 찾는다.
6. 증거가 나올 때까지 제안은 적용하지 않는다.
```

### 9.4 반복 실패의 이중고리

같은 목표와 규칙을 유지한 채 행동만 고치는 것은 단일고리 학습이다. 같은 종류의 실패가 반복되면, 목표·성공 기준·규칙·가정 자체도 잘못되었는지 묻는 이중고리 학습을 연다. [10]

이중고리는 매 작업의 의식이 아니다. 반복 예외, 같은 실패의 재발, 국소 수리가 새 문제를 만드는 관찰이 있을 때만 연다. 그렇지 않으면 회고 자체가 또 하나의 증식이 된다.

## 10. 교차 검증: 다수결이 아니라 독립 반증

두 AI가 같은 결론을 냈다고 검증된 것이 아니다. 같은 입력·용어·실패 프레임을 공유하면 같은 오해를 반복할 수 있다.

```text
작업자:
  현재 바이트, 목적, 제안, 근거, 미검증을 제시한다.

독립 반증자:
  작업자의 대화와 수리 의도를 받지 않는다.
  원문과 실제 흐름으로 “이 제안이 틀렸다면 어디서 어떻게 실패하는가?”를 찾는다.
  해결안을 만들지 않고 실패 경로와 증거만 낸다.

판정자:
  결론의 개수를 세지 않는다.
  항목을 원인 소유자별로 묶고, 현재 재현·원문 충돌·실측 중 무엇이 있는지 판정한다.
```

반증 소견은 아래를 모두 가져야 수정 권한을 얻는다.

```text
원문 또는 실행 좌표
구체적 실패 장면
그 장면이 생기는 원인 메커니즘
적용되지 않는 범위
자기 소견을 기각할 수 있는 반대 증거
```

없는 경우 그 소견은 “가능한 우려”로 기록할 수는 있어도 규칙·코드·기계를 늘릴 근거가 아니다.

## 11. AI에게 주는 실행 규약

```text
1. 목적·금지·성공 증거가 없으면 추측하지 말고 미결정으로 둔다.
2. 과거 실패를 현재 규칙으로 취급하지 말고 사실·해석·미검증으로 나눈다.
3. 문제를 해결안으로 쓰지 말고, 상황·영향·성공·반례가 있는 문제 주장으로 쓴다.
4. 첫 수리안을 정답으로 두지 말고 국소·상위 계약·비문제 가설을 비교한다.
5. 한 탐구 단위에는 하나의 미지와 하나의 판정만 둔다.
6. 구현 전에 수단 가설, 반례, 가장 싼 판별 관찰을 쓴다.
7. 의미·전달·행동·효과의 증거를 서로 바꾸어 부르지 않는다.
8. 발견이 기존 기획보다 좋아 보여도 승격 조건을 만족하기 전에는 범위를 넓히지 않는다.
9. 실패를 발견하면 먼저 소유 층을 분류하고, 그 층으로 되돌린다.
10. 관찰된 실패·현재 모순·소유자가 명시한 요구·실제 외부 제약 중 하나와 구체적 위해 경로 없이는 새 규칙·검사·예외를 만들지 않는다.
11. 같은 수리가 반복되거나 증식 신호가 보이면 확장을 멈추고 원인 가설을 다시 세운다.
12. 교차 검증은 독립된 실패 경로와 증거의 비교이지, AI 결론의 다수결이 아니다.
13. 완료 보고에는 지원된 것, 반증된 것, 미결정, 미검증을 함께 쓴다.
14. 사람에게 설명할 때는 결론·관찰·이유·미확인을 분리하고, AI식 압축어보다 실제 대상·행동·영향을 먼저 쓴다.
15. 행동을 지시하는 문장만 조건 → 주체 → 행동 → 결과 → 경계로 닫는다. 배경과 판단 이유까지 준코드로 바꾸지 않는다.
16. 값·상태·순서처럼 결정 가능한 사실은 가능한 한 선언·스키마·코드·검사 한 곳이 소유하게 하고, 산문은 그 사실을 독립적으로 다시 규정하지 않는다.
17. 다른 AI의 해석 시험은 행동 차이를 찾는 관찰이다. 같은 답은 보증이 아니며, 다른 답도 실제 행동 영향 없이는 새 규칙의 근거가 아니다.
18. 현재 작업에는 0.1의 공통 핵심과 필요한 절만 투영한다. 전체 문서를 읽거나 모든 양식을 채운 사실을 품질 증거로 쓰지 않는다.
19. 새 인터페이스·중간 표현·기계를 추가할 때는 그것이 제거하는 산문·판단·왕복·복구 비용과 새로 만드는 비용을 함께 센다.
20. 상태는 다음 행동·재개·동시성을 바꿀 때만 저장하고, 여러 작업이 하나의 전역 current 상태를 공유하게 하지 않는다.
21. 정확한 출력 형태는 가능한 경우 renderer가 소유하고, AI는 기계가 판정할 수 없는 의미를 맡는다. 자연어의 진실성까지 형식 검사로 주장하지 않는다.
22. 테스트는 공격할 주장과 실패 시 바뀔 결정을 가져야 한다. 통과 수나 내부 과정의 완전한 재현을 제품 완성도로 승격하지 않는다.
23. 실패한 체계를 greenfield로 다시 만들 때 과거 요구·관찰·검증된 불변식은 보존하되, 과거 구조·호환·테스트 기대값은 독립 근거 없이 새 기준선으로 가져오지 않는다.
```

## 12. 이 체계의 자체 점검

이 문서는 아래 장면들을 끝까지 걸어 본 기준으로 구성했다.

| 장면 | 이 체계가 요구하는 다음 행동 | 막으려는 실패 |
|---|---|---|
| 과거 수리가 많지만 실패 원인이 불명확함 | 실패를 사실·해석·미검증으로 재구성하고 H1/H2/H3를 판별 | 과거 구조를 원칙으로 보존하거나 모두 폐기 |
| AI가 규칙을 지키지 않음 | 의미·전달·행동·효과 중 어느 면이 깨졌는지 먼저 분류 | 산문·검사를 무작정 추가 |
| 구현 중 더 좋아 보이는 구조를 발견함 | 승격 조건을 확인하고 충족하지 못하면 기록만 함 | 현재 카드가 새 프로젝트로 팽창 |
| 리뷰어가 “혼동 가능”을 지적함 | 좌표·실패 장면·원인·반대 증거를 요구 | 근거 없는 일반 규칙과 검증 루프 증식 |
| 검증 중 현재 범위 밖의 새 문제를 발견함 | 폐쇄 계약의 편입 조건을 대조하고, 결론을 뒤집지 않으면 관찰로 분리 | 새 발견마다 현재 수리·검증이 무한히 재개 |
| AI의 설명이 압축적이어서 사람이 판단하기 어려움 | 결론·관찰·이유·미확인을 분리해 사람말로 다시 쓴다 | 전문성을 잃는 과도한 단순화 또는 AI식 관리 언어의 누적 |
| 새 AI가 문장을 다르게 읽음 | 행동 차이부터 확인하고, 목적·행동 계약·결정 가능한 사실 중 맞는 소유자만 보완 | 표현 취향을 규칙으로 만들거나 모든 산문을 형식 언어로 전환 |
| 실패한 시스템을 처음부터 다시 만들려 함 | 과거 요구·관찰·불변식만 문제 자료로 보존하고 새 수직 흐름을 독립 설계 | 실패한 구조·호환·테스트 기대값이 새 설계를 선점 |
| AI가 도구가 이미 아는 값을 다시 읽고 입력함 | 작업면의 입력·판단·결과를 나누고 새 장치가 제거하는 context·왕복을 계산 | 기계가 추론을 덜지 못하고 의식과 매뉴얼만 추가 |
| 여러 세션이 같은 작업 상태를 갱신함 | 상태를 task·artifact별로 분리하고 revision 충돌을 드러냄 | 전역 current 상태의 덮어쓰기와 거짓 완료 |
| 정해진 양식을 AI가 반복 작성함 | 의미 필드와 결정 가능한 렌더 형식을 분리 | AI가 형식을 외우거나 모든 의미가 경직된 form으로 축소 |
| 많은 테스트가 통과했지만 실제 사용이 실패함 | 테스트가 공격하는 주장과 증거 층을 밝히고 대표 행동·효과를 별도 관찰 | 구조 점수표를 AI 행동과 사용자 효과의 증거로 오인 |

이 체계가 아직 보장하지 않는 것도 명시한다.

- AI가 이 문서를 읽기만 해도 올바른 문제를 항상 발견한다는 보장은 없다.
- 성공 기준 자체가 잘못되었다면, 소유자·실제 사용자·운영 관찰 없이는 고칠 수 없다.
- 탐구 카드와 교차 검증도 비용이므로, 관찰된 위험보다 비싼 절차로 일반화하면 안 된다.
- 이 체계의 효과는 실제 작업에서 재작업률, 잘못된 추가물, 검증 누락, 사용자·AI 행동의 변화로 측정되어야 한다.
- 해석 안정성 절차도 임의의 AI가 같은 뜻을 읽게 증명하지는 못한다. 서로 다른 다음 행동을 줄이고 발견하는 데까지만 주장할 수 있다.

### 12.1 이 체계 자체도 효과를 검증해야 한다

논리적으로 좋은 문서와 실제 개발 비용을 줄이는 문서는 같지 않다. 이 체계를 중요한 기준으로 채택하더라도 다음 세 조건을 가능한 한 같은 작업 유형과 성공 기준에서 비교한다.

```text
기준안: 별도 체계 없이 현재 작업 지시만 제공
최소 투영: 0.1에서 선택된 공통 핵심과 관련 절만 제공
전체 참조: 기반·고위험 작업에서 전체 원문을 참조 가능하게 제공
```

비교할 것은 문서를 잘 요약했는지나 카드를 많이 작성했는지가 아니다.

- 목적 또는 범위를 소유자와 다시 맞춰야 했던 횟수
- 근거 없는 규칙·검사·예외와 재작업의 수
- 고정·조건부 컨텍스트, tool 왕복과 복구 비용
- 같은 입력에서 행동을 바꾸는 해석 차이
- 실제 결과의 계약 위반과 사용자 문제 개선

최소 투영이 같은 결과를 더 적은 비용으로 만들면 그것을 기본 진입으로 쓴다. 전체 참조가 기반 기획·반복 실패·고위험 경계에서만 추가 가치를 보이면 그 조건에서만 연다. 이 비교 없이 “문서가 합리적으로 보인다”는 이유만으로 효과가 증명되었다고 말하지 않는다.

## 13. 한 문장 요약

> 과거 실패는 증거로 재구성하고, 문제는 정의·전제·반례로 다시 만들며, 수단은 경쟁 가설과 판별로 고르고, 구현의 발견은 올바른 소유자에게 돌려보내며, 새 장치는 관찰된 실패를 더 작은 전체 복잡성으로 없앨 때만 추가한다.
